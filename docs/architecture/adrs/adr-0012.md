# ADR-0012: PDF Parser Selection

**Status:** Accepted
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

The PDF importer requires a parser that extracts text and metadata from real-world PDFs. These documents come from diverse sources — lab reports, academic papers, scanned forms, government filings — and frequently contain malformed structures that strict parsers reject. The parser must handle corrupted cross-reference tables, non-standard xref streams, and truncated headers without external system dependencies.

## Decision

Use `pdf_oxide` as the PDF parser for the import pipeline. It is a pure-Rust library with built-in text extraction, XMP metadata support, and dedicated xref reconstruction for malformed files.

```rust
let doc = PdfDocument::open(path)?;
let text = doc.extract_all_text()?;
if let Some(xmp) = XmpExtractor::extract(&doc)? {
    // title, author, creation_date from XMP
}
```

`pdf_oxide` provides 100% pass rate on a 3,830-PDF test corpus, handles encrypted PDFs (RC4, AES-128/256), and includes reading-order text extraction for multi-column layouts. No external binaries required.

## Alternatives Considered

### `lopdf` (tried, replaced)

The initial implementation used `lopdf` for text extraction and metadata parsing. `lopdf` is pure Rust and fast, but strict about PDF structure. It rejects files with malformed cross-reference tables — a common defect in real-world PDFs that render fine in consumer readers. On a 3,830-PDF benchmark corpus, `lopdf` passes only 80.2% of files. Real import batches regularly contained failures.

### `pdftotext` / Poppler CLI (tried, replaced)

A fallback to `pdftotext` was added to rescue files `lopdf` rejected. `pdftotext` is battle-tested and lenient, but requires `poppler-utils` installed as a system binary. This creates a deployment dependency — unavailable in minimal Docker images, CI environments, and clean installs. Two parsing paths also doubled maintenance surface.

### `pdfium-render` (considered)

Wraps Google's Chromium PDFium, the most battle-tested PDF parser available. `RebuildCrossRef()` provides the most aggressive malformed-file recovery. Rejected because it requires a ~15MB C++ shared library (`libpdfium.so`), complex build configuration, and binary distribution. Overkill for text extraction.

### `pdf-extract` (considered)

Built on top of `lopdf` — calls `lopdf::Document::load()` internally. Inherits the same strictness and fails on the same malformed PDFs. Zero additional coverage. Rejected.

## Consequences

### Positive
- Malformed PDFs are handled natively with xref reconstruction.
- No external system binary required — pure Rust dependency.
- Built-in XMP metadata extraction and reading-order text extraction.
- Encrypted PDF support without additional configuration.

### Negative
- Larger dependency tree (~80 crates) compared to `lopdf` (~15 crates).
- Single primary maintainer (Yury Fedoseev) — mitigated by adoption in RAGFlow, AFFiNE, xAI, and Neo4j Labs.
- MSRV 1.88 (workspace uses Rust 1.97.1, so no practical constraint).

### Risks
- Supply chain surface from larger dependency tree. Mitigated by `pdf_oxide`'s `cargo-deny` configuration, fuzz testing in CI, and professional security policy.
- Single-maintainer bus factor. Upgrade path: `pdfium-render` if `pdf_oxide` stalls.
