# ADR-0013: Composite Entity Resolution with Weighted Signals

**Status:** Accepted
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

The entity resolution system uses a single Jaro-Winkler similarity score on normalized titles with a 0.95 threshold. This produces two classes of errors:

**False merges (wrong):** Different revisions of the same document merge because the titles are 97%+ similar (e.g., "CV rev.0622" vs "CV rev.0703"). Different language variants merge (e.g., "Backend PHP - Spanish" vs "Backend PHP - English").

**Missed merges:** Documents with semantically identical titles but different phrasing are rejected when Jaro-Winkler falls below threshold.

The current pipeline has three strategies (Exact → Normalized → Fuzzy) that stop at the first match. `ContentMatch` (Jaccard word overlap) exists but is disabled. There is no multi-signal scoring and no review path for ambiguous cases.

## Decision

Replace the single-metric threshold with a composite scoring model that combines multiple signals and introduces a three-zone decision model.

### 1. Composite Scoring

Replace single Jaro-Winkler with weighted composite:

| Signal                 | Weight | Implementation                                               |
| ---------------------- | ------ | ------------------------------------------------------------ |
| Title similarity       | 0.40   | Jaro-Winkler + Levenshtein (existing)                        |
| Content similarity     | 0.30   | Jaccard word overlap (existing, currently disabled)          |
| Metadata overlap       | 0.20   | Language match, file size proximity, creation date proximity |
| Structural fingerprint | 0.10   | Page count, binary content size                              |

Composite score = Σ(weight_i × score_i) for all available signals. Missing signals redistribute their weight proportionally.

### 2. Three-Zone Decision Model

```
Score >= 0.92  →  Auto-merge (high confidence)
0.78 <= score < 0.92  →  Queue for human review
Score < 0.78  →  Reject (no match)
```

Exact title matches (title_score == 1.0) always merge regardless of composite score, since identical titles are the strongest signal of identity. This handles the common case of re-importing the same file with updated content.

### 3. Metadata Overlap Signal

Compute pairwise metadata similarity:
- **Language match:** +0.3 if same language, 0.0 if different
- **File size proximity:** 1.0 - |log2(size_a) - log2(size_b)| / 10.0, clamped to [0, 1]
- **Date proximity:** 1.0 - days_apart / 365.0, clamped to [0, 1]

Metadata score = (language + file_size + date) / 3.0

### 4. Resolution Strategy Pipeline

The resolver uses a hybrid approach:

**Phase 1 (short-circuit):** Exact → Normalized → Fuzzy. If any strategy produces a match above its threshold, return immediately. This preserves the existing behavior for high-confidence matches.

**Phase 2 (composite):** If Phase 1 produces no candidates, compute composite scores for all same-type entities. This catches fuzzy matches that the single-metric pipeline misses, while routing ambiguous cases to the review zone.

## Alternatives Considered

### Approach 1: Higher Threshold
- Pros: Minimal change, solves the immediate problem.
- Cons: Single signal still fragile. No review path for ambiguous cases.
- Why not chosen: Band-aid, not architecture.

### Approach 2: Three-Zone Model Without Composite Scoring
- Pros: Adds review path. Simple to implement.
- Cons: Still relies on single Jaro-Winkler signal. Review queue gets noisy matches.
- Why not chosen: Half the solution.

### Approach 3: Revision Detection via Regex
- Pros: Catches known revision patterns.
- Cons: Arbitrary pattern matching. Creates if-statements based on patterns we detect. Fragile — misses novel revision formats. Violates the principle that scoring should be signal-based, not pattern-based.
- Why not chosen: Revisions naturally fall into the review zone via composite scoring because they have high title similarity but different content/metadata. The three-zone model handles this correctly without special-casing.

### Approach 4: Composite Scoring (chosen)
- Pros: Multi-signal robustness. Handles revisions, language variants, and semantic duplicates. Review path for ambiguity. No arbitrary pattern matching.
- Cons: More complex. Weights need tuning on labeled data.
- Why chosen: Addresses all three error classes. Infrastructure already exists (ContentMatch, metadata, structural data all available).

## Consequences

### Positive
- Different revisions naturally route to the review zone (high title similarity, different content/metadata).
- Language variants (Spanish/English) are distinguished by the language signal.
- True duplicates with different filenames are caught by content + title composite.
- Ambiguous cases route to human review instead of silent wrong merges.
- Existing signals (Jaro-Winkler, Jaccard, metadata) are already implemented.
- No arbitrary pattern matching — all decisions are signal-based.

### Negative
- Composite weights require tuning. Initial weights are heuristic; should be validated on labeled data.
- Review queue requires UI or CLI support (deferred — initial implementation logs candidates).
- More parameters to maintain.

### Risks
- Heuristic weights may not generalize across entity types. Mitigation: per-type weight overrides via ResolutionConfig.
- Review queue without UI may be ignored. Mitigation: log review candidates to stderr with clear formatting.
