# ADR-0014: Bounded Graph Traversal via Recursive CTE

**Status:** Proposed
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

PRD-0001 builds the knowledge graph. PRD-0002 makes it trustworthy. But a knowledge graph you cannot explore is just a database. Users need to navigate relationships between entities — from a paper, find its authors; from a concept, find all implementing tools; from an organization, find all contributions.

The current system provides only single-hop queries via `RelationshipRepository::by_source()` and `by_target()`. Multi-hop traversal requires application-level loops, which are inefficient, unbounded, and cannot detect cycles.

## Decision

We implement N-hop relationship traversal using recursive Common Table Expressions (CTEs) in SQLite, with bounded depth, cycle detection via deduplication, and configurable filters.

### Traversal Query

```sql
WITH RECURSIVE traverse(id, depth) AS (
    SELECT id, 0 FROM entities WHERE id = ?1
    UNION
    SELECT r.target_id, t.depth + 1
    FROM relationships r
    JOIN traverse t ON r.source_id = t.id
    WHERE t.depth < ?2
      AND r.is_active = 1
)
SELECT DISTINCT e.*, t.depth
FROM traverse t
JOIN entities e ON e.id = t.id
WHERE e.is_active = 1
ORDER BY t.depth;
```

### Traversal Port

A new `TraversalPort` trait in `knowledge-core` defines the traversal interface:

```rust
#[async_trait]
pub trait TraversalPort: Send + Sync {
    async fn traverse(
        &self,
        start_id: &str,
        depth: u32,
        filter: Option<TraversalFilter>,
    ) -> Result<TraversalResult>;
}

pub struct TraversalFilter {
    pub relationship_types: Option<Vec<RelationshipType>>,
    pub entity_types: Option<Vec<EntityType>>,
}

pub struct TraversalResult {
    pub nodes: Vec<TraversedEntity>,
    pub edges: Vec<TraversedRelationship>,
    pub depth_used: u32,
}

pub struct TraversedEntity {
    pub entity: Entity,
    pub depth: u32,
}

pub struct TraversedRelationship {
    pub relationship: Relationship,
    pub from_depth: u32,
    pub to_depth: u32,
}
```

### Bounded Depth

- Default depth: 3 hops
- Maximum depth: configurable, capped at 10
- Depth parameter is enforced in the CTE's `WHERE` clause
- SQLite's default recursion limit (1000) is not a concern at depth ≤ 10

### Cycle Detection

Cycles are handled by `SELECT DISTINCT` in the CTE. If entity B is reachable from A via two different paths, it appears once at the shallowest depth. No explicit visited set is needed.

### Direction

Traversal is directional by default — follows `source_id → target_id`. Bidirectional traversal (following edges in both directions) is supported via a configuration flag but is not the default, as relationship direction carries semantic meaning in the knowledge model.

### Filtering

- **Relationship type filter:** Only follow edges of specified types (e.g., `--type references`)
- **Entity type filter:** Only return entities of specified types (e.g., `--entity-type concept`)
- Filters are applied in the CTE's `WHERE` clause for efficient pruning

### Performance Targets

- Target: < 100ms for 2 hops at 100K entities
- Target: < 500ms for 3 hops at 100K entities
- Indexes required: `idx_relationships_source` on `relationships(source_id)`, `idx_relationships_target` on `relationships(target_id)`, `idx_relationships_active` on `relationships(is_active)`
- The CTE's branching factor is bounded by average relationship degree, not total entity count

## Alternatives Considered

### Approach 1: Application-level BFS/DFS
- Pros: More flexible traversal logic, can implement custom pruning.
- Cons: N+1 queries, manual cycle detection, harder to test, performance degrades with graph size.
- Why not chosen: Recursive CTEs are a single SQL statement — simpler, faster, and testable.

### Approach 2: Closure Table (pre-computed paths)
- Pros: O(1) path lookups, no recursion at query time.
- Cons: Expensive writes (every new relationship requires updating the closure table), significant storage overhead, over-engineering for current scale (< 100K entities).
- Why not chosen: Can be added later as an optimization without changing the traversal port.

### Approach 3: Dedicated Graph Database (Neo4j, FalkorDB)
- Pros: Cypher query language is more expressive for complex graph patterns.
- Cons: Violates storage independence (ADR-0002), adds infrastructure dependency, breaks the single-binary deployment model.
- Why not chosen: Architectural principle — storage is an implementation detail, not the architecture.

### Approach 4: Recursive CTE in SQLite (chosen)
- Pros: Single SQL statement, no new dependencies, cycle detection via `UNION`, bounded by depth parameter, compatible with existing SQLite adapter.
- Cons: Less expressive than Cypher for complex path patterns, performance degrades at depth > 5 with high branching factor.
- Why chosen: Fits the bounded depth requirement, zero new dependencies, testable with existing infrastructure.

## Consequences

### Positive
- Single SQL statement for entire traversal — no application-level loops
- Cycle detection is free via `UNION` deduplication
- Bounded depth prevents unbounded computation
- Filtering in the CTE reduces data scanned at each recursion step
- Compatible with existing SQLite adapter — no new storage engine needed

### Negative
- Recursive CTEs are less expressive than Cypher pattern matching (e.g., "find all paths where every intermediate node is a specific type" is difficult in SQL)
- Bidirectional traversal requires a `CASE` expression, slightly more complex query
- Performance degrades with high branching factor at depth > 4

### Risks
- At depth 5+ with high branching factor, result set grows exponentially. The depth cap of 10 is a hard limit, but practical use should stay at depth 3-4.
- SQLite's write lock is process-wide. Concurrent traversals during writes may contend. WAL mode mitigates this for read-heavy workloads.
