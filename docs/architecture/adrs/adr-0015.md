# ADR-0015: View Projection System

**Status:** Proposed
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

The knowledge graph contains canonical entities, relationships, and components. But users interact with knowledge through projections — a tree for hierarchical navigation, a table for comparison, a graph for relationship exploration, a timeline for temporal ordering. Without projections, the system is a backend with no experience.

The architecture documents (pipeline.md, philosophy.md) establish that views are derived data — they render knowledge, they never own it. Every view is disposable and rebuildable from canonical data.

## Decision

We introduce a `ViewAdapter` trait system where each view type is an independent implementation that renders canonical data into a specific projection format. Views are updated event-driven — when canonical data changes, views are invalidated and rebuilt.

### ViewAdapter Trait

```rust
#[async_trait]
pub trait ViewAdapter: Send + Sync {
    /// The name of this view (e.g., "tree", "graph", "table", "timeline")
    fn name(&self) -> &str;

    /// Render the view with the given filter
    async fn render(&self, filter: &ViewFilter) -> Result<ViewOutput>;

    /// Notify the view that canonical data has changed.
    /// The view invalidates its derived data and rebuilds on next render.
    async fn on_event(&self, event: &Event) -> Result<()>;
}
```

### ViewFilter

```rust
pub struct ViewFilter {
    pub entity_types: Option<Vec<EntityType>>,
    pub tags: Option<Vec<String>>,
    pub relationship_types: Option<Vec<RelationshipType>>,
    pub max_depth: Option<u32>,
    pub start_entity_id: Option<String>,
    pub sort_by: Option<String>,
    pub sort_order: Option<SortOrder>,
    pub search_query: Option<String>,

pub enum SortOrder { Asc, Desc }
```

### ViewOutput

Each view produces a `ViewOutput` — an enum of projection-specific data:

```rust
pub enum ViewOutput {
    Tree(TreeData),
    Graph(GraphData),
    Table(TableData),
    Timeline(TimelineData),
}

pub struct TreeData {
    pub roots: Vec<TreeNode>,
}

pub struct TreeNode {
    pub entity: Entity,
    pub children: Vec<TreeNode>,
}

pub struct GraphData {
    pub nodes: Vec<GraphNode>,
    pub edges: Vec<GraphEdge>,
}

pub struct GraphNode {
    pub entity: Entity,
    pub label: String,
    pub node_type: String,
}

pub struct GraphEdge {
    pub source_id: String,
    pub target_id: String,
    pub relationship_type: String,
    pub label: String,
}

pub struct TableData {
    pub columns: Vec<TableColumn>,
    pub rows: Vec<TableRow>,
}

pub struct TableColumn {
    pub name: String,
    pub sortable: bool,
}

pub struct TableRow {
    pub cells: Vec<String>,
}

pub struct TimelineData {
    pub entries: Vec<TimelineEntry>,
}

pub struct TimelineEntry {
    pub entity: Entity,
    pub timestamp: String,
    pub label: String,
}
```

### Built-in Views

| View | Input Data | Output Format | Grouping |
|------|-----------|---------------|----------|
| Tree | Entity type + collection membership | Indented text (CLI) | Entity type → entities |
| Graph | Entities + relationships (from traversal) | Adjacency list (CLI) | Nodes + edges |
| Table | Entity + component data | Tabular text (CLI) | Flat rows |
| Timeline | Entity + timeline component | Chronological list (CLI) | Temporal order |

### View Synchronization

Views are updated through the existing event system (ADR-0004). When canonical data changes:

1. An event is emitted (`EntityCreated`, `ComponentUpdated`, etc.)
2. The view registry notifies all registered view adapters
3. Each view adapter calls `on_event()` and invalidates its derived data
4. On next `render()` call, the view rebuilds from canonical data

This is eventual consistency — views may be briefly stale between event and rebuild. This is acceptable per ADR-0004's design.

### View Registry

```rust
pub struct ViewRegistry {
    views: HashMap<String, Box<dyn ViewAdapter>>,
}

impl ViewRegistry {
    pub fn register(&mut self, view: Box<dyn ViewAdapter>);
    pub async fn render(&self, name: &str, filter: &ViewFilter) -> Result<ViewOutput>;
    pub async fn notify_event(&self, event: &Event) -> Result<()>;
    pub fn list_views(&self) -> Vec<String>;
}
```

### Layer Ownership

View projections span two layers:
- **Layer 6 (Derivation):** View adapters that read canonical data and produce derived output
- **Layer 7 (Presentation):** CLI formatting that renders `ViewOutput` as terminal text

The `ViewAdapter` trait belongs to Layer 6. CLI rendering belongs to Layer 7.

## Alternatives Considered

### Approach 1: Incremental View Maintenance
- Pros: Faster updates — only recompute what changed.
- Cons: Requires tracking dependencies between canonical data and view entries. Significantly more complex. Over-engineering for current scale where full rebuilds are fast.
- Why not chosen: Full rebuild from canonical data is simpler and sufficient at < 100K entities.

### Approach 2: Materialized Views in SQLite
- Pros: Database-managed view storage.
- Cons: SQLite does not support materialized views natively. Temporary tables couple views to storage. Violates storage independence (ADR-0002).
- Why not chosen: Storage independence principle.

### Approach 3: Separate View Database
- Pros: Isolated view storage, no performance impact on canonical queries.
- Cons: Violates derived data disposability — views should be rebuildable, not persisted as authoritative. Adds infrastructure complexity.
- Why not chosen: Views are derived data. Derived data lives in the same storage layer as canonical data.

### Approach 4: Trait-based ViewAdapters (chosen)
- Pros: Each view is independent, testable, disposable. Adding a new view requires only implementing the trait. Event-driven synchronization leverages existing infrastructure.
- Cons: Views rebuild from scratch on each render (no incremental updates). The `ViewOutput` enum couples view types at the type level.
- Why chosen: Follows the projection principle — views render knowledge, they never own it. Maximum extensibility with minimum core changes.

## Consequences

### Positive
- Adding a new view type requires only implementing `ViewAdapter` — no core changes
- Views are disposable — any view can be deleted and rebuilt from canonical data
- Event-driven synchronization keeps views eventually consistent
- The trait-based design enables testing views with mock canonical data

### Negative
- Views rebuild from scratch on each render (no incremental updates initially)
- Event-driven synchronization has eventual consistency — views may be briefly stale
- The `ViewOutput` enum couples view types at the type level (can be refactored to trait objects later if needed)

### Risks
- Rebuilding large views from scratch may be slow. Mitigation: views are bounded by filters (entity type, tags, max depth). Unbounded views are not supported.
