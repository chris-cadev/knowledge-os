# ADR-0016: Plugin System Architecture

**Status:** Proposed
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

Knowledge OS must be extensible. Users need to add new import formats, new AI providers, new view types, and new storage adapters without modifying the core. The architecture documents (extensibility.md, philosophy.md) establish that the core is stable and the ecosystem provides variety.

The current system has `ImportAdapter` as a trait but no plugin infrastructure — importers are compiled into the binary. There is no discovery, no manifest, no capability negotiation, and no isolation.

## Decision

We introduce a plugin system with in-process plugins (trait objects compiled into the binary), TOML manifests for metadata, a capability registry for routing, and error boundaries for isolation. Dynamic library loading is deferred to a future phase.

### Why In-Process First

Rust has no stable ABI. Dynamic library loading (`libloading`/`dlopen`) requires plugin and host to be compiled with the exact same compiler version and dependency versions. This is fragile and adds significant complexity (FFI shims, memory ownership across allocator boundaries, ABI version negotiation).

In-process plugins (trait objects) provide:
- Type safety at compile time
- No ABI instability
- Rust-native error handling (`Result<T, PluginError>`)
- The same capability registry and manifest system
- Easy to test and debug

Dynamic loading can be added later as an optional enhancement for untrusted plugins.

### Plugin Manifest

Every plugin declares a TOML manifest:

```toml
[plugin]
name = "markdown-importer"
version = "0.1.0"
description = "Import Markdown files as knowledge entities"
author = "Knowledge OS"
license = "MIT"

[plugin.capabilities]
importers = ["markdown"]
```

The manifest is parsed at startup and validated against the plugin's declared capabilities. The manifest does not contain executable code — it is metadata only.

### Plugin Trait

Plugins implement a `Plugin` trait:

```rust
pub trait Plugin: Send + Sync {
    /// Return the manifest for this plugin
    fn manifest(&self) -> &PluginManifest;

    /// Activate the plugin. Called once at startup after registration.
    fn activate(&self) -> Result<()>;

    /// Deactivate the plugin. Called once at shutdown.
    fn deactivate(&self) -> Result<()>;
}
```

### Capability Registry

The capability registry maps capabilities to plugin implementations:

```rust
pub struct CapabilityRegistry {
    importers: HashMap<String, Box<dyn ImportAdapter>>,
    renderers: HashMap<String, Box<dyn ViewAdapter>>,
    ai_providers: HashMap<String, Box<dyn AiAdapter>>,
    vector_stores: HashMap<String, Box<dyn VectorStore>>,
}

impl CapabilityRegistry {
    pub fn register_importer(&mut self, format: String, adapter: Box<dyn ImportAdapter>);
    pub fn register_renderer(&mut self, name: String, adapter: Box<dyn ViewAdapter>);
    pub fn register_ai_provider(&mut self, name: String, adapter: Box<dyn AiAdapter>);
    pub fn register_vector_store(&mut self, name: String, adapter: Box<dyn VectorStore>);

    pub fn get_importer(&self, format: &str) -> Result<&dyn ImportAdapter>;
    pub fn get_renderer(&self, name: &str) -> Result<&dyn ViewAdapter>;
    pub fn get_ai_provider(&self, name: &str) -> Result<&dyn AiAdapter>;
    pub fn get_vector_store(&self, name: &str) -> Result<&dyn VectorStore>;
}
```

### Plugin Loading

```
Startup
  |
  Scan plugin directories (configurable via KOS_PLUGIN_PATH)
  |
  Parse TOML manifests
  |
  Validate capabilities (manifest must match implemented traits)
  |
  Instantiate plugin structs (in-process, no dynamic loading)
  |
  Register with capability registry
  |
  Call activate() on each plugin
```

### Plugin Sandboxing

Plugins run in the same process but are isolated through:

1. **Trait-based interfaces:** Plugins communicate through trait methods only. No shared mutable state between plugins.
2. **Error boundaries:** Plugin errors are caught and logged, not propagated. A failing plugin does not crash the core system.
3. **Resource limits:** Configurable per-plugin timeout on async operations.
4. **No direct storage access:** Plugins access storage through port traits, never through direct database connections.

```rust
pub async fn safe_call<F, T>(plugin_name: &str, f: F) -> Result<Option<T>>
where
    F: std::future::Future<Output = Result<T>>,
{
    match tokio::time::timeout(Duration::from_secs(30), f).await {
        Ok(Ok(result)) => Ok(Some(result)),
        Ok(Err(e)) => {
            log::error!("Plugin '{}' failed: {}", plugin_name, e);
            Ok(None)
        }
        Err(_) => {
            log::error!("Plugin '{}' timed out", plugin_name);
            Ok(None)
        }
    }
}
```

### Plugin Lifecycle

```
Discovery → Registration → Activation → Execution → Deactivation
```

- **Discovery:** Parse TOML manifests from plugin directories
- **Registration:** Register capabilities with the capability registry
- **Activation:** Call `activate()` — plugin initializes resources
- **Execution:** Plugin handles requests through its capability
- **Deactivation:** Call `deactivate()` — plugin releases resources

### Plugin Discovery

Plugins are discovered from directories specified in configuration:
- Default: `~/.config/knowledge-os/plugins/`
- Override: `KOS_PLUGIN_PATH` environment variable
- Each plugin is a directory containing `plugin.toml` and a compiled library

For in-phase implementation, plugins are compiled into the binary as feature flags. Plugin directories are for future dynamic loading.

### ImportAdapter as First Plugin

The existing `ImportAdapter` trait becomes the first plugin capability. The Markdown importer is registered as a plugin:

```rust
pub struct MarkdownImporterPlugin;

impl Plugin for MarkdownImporterPlugin {
    fn manifest(&self) -> &PluginManifest {
        &PluginManifest {
            name: "markdown-importer".into(),
            version: "0.1.0".into(),
            description: "Import Markdown files".into(),
            author: "Knowledge OS".into(),
        }
    }
    fn activate(&self) -> Result<()> { Ok(()) }
    fn deactivate(&self) -> Result<()> { Ok(()) }
}

impl ImportAdapter for MarkdownImporterPlugin {
    // Delegates to existing MarkdownImporter logic
}
```

## Alternatives Considered

### Approach 1: Dynamic Library Loading (`libloading`)
- Pros: Plugins can be added at runtime without recompilation. True extensibility.
- Cons: Rust has no stable ABI. Requires C ABI shims, FFI safety, memory ownership across allocator boundaries. ABI version negotiation is complex and fragile. Compiler version must match between host and plugin.
- Why not chosen: Deferred to future phase. The capability registry design is compatible with dynamic loading when added.

### Approach 2: WebAssembly Plugins
- Pros: Sandboxed execution, language-agnostic, portable.
- Cons: High overhead for in-process calls. Limited Rust interop (WASI). Complex build pipeline. Over-engineering for current needs.
- Why not chosen: Too complex for initial implementation. In-process plugins provide the same capability routing with less complexity.

### Approach 3: Trait Objects Without Manifests
- Pros: Simpler — no TOML parsing, no metadata.
- Cons: Loses plugin discovery (name, version, description), version compatibility checking, and capability routing metadata. The system cannot enumerate or describe loaded plugins.
- Why not chosen: Manifests are needed for `kos plugin list`, version compatibility, and future dynamic loading.

### Approach 4: In-Process Plugins with Manifests (chosen)
- Pros: Type safety, no ABI instability, Rust-native error handling, capability routing, plugin metadata, easy to test. Compatible with future dynamic loading.
- Cons: All plugins compiled into the binary — cannot be added at runtime. All plugins share process memory — no memory isolation.
- Why chosen: Maximum simplicity with full capability routing. Dynamic loading is a future enhancement, not a current requirement.

## Consequences

### Positive
- Extensibility without core changes — new importers, renderers, AI providers are plugins
- Type safety via trait objects — no FFI, no ABI instability
- Error isolation — plugin failures don't crash the core
- The capability registry provides a single lookup point for all capabilities
- In-process plugins are easy to test and debug

### Negative
- In-process plugins are compiled into the binary — cannot be added at runtime
- All plugins share the same process memory — no memory isolation
- Plugin conflicts (two plugins claiming the same capability) require resolution logic

### Risks
- Plugin quality is not vetted by the system. Mitigation: community review, documented plugin guidelines, and the capability registry can enforce version compatibility.
