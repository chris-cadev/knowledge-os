# ADR-0017: Semantic Search via Embeddings

**Status:** Proposed
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

Keyword search (FTS5) finds entities containing specific terms. But knowledge retrieval requires finding entities that are conceptually related, even when they use different terminology. A search for "machine learning" should surface papers about "neural networks," "deep learning," and "gradient descent" — not just papers containing the exact phrase.

Semantic search uses embedding vectors to represent entity meaning. Two entities with similar meanings have similar vectors, regardless of exact keyword overlap.

## Decision

We implement semantic search through an embedding pipeline: extract text from entities, generate embedding vectors via a configurable AI provider, store vectors, and rank results by cosine similarity. Hybrid search combines keyword (BM25) and semantic (cosine) results via Reciprocal Rank Fusion.

### Embedding Component

The existing `ComponentType::Embedding` stores the vector:

```rust
pub struct EmbeddingData {
    pub vector: Vec<f32>,
    pub model: String,
    pub generated_at: String,
}
```

### AiAdapter Trait

AI provider plugins implement the `AiAdapter` trait:

```rust
#[async_trait]
pub trait AiAdapter: Send + Sync {
    /// Generate an embedding vector from text content
    async fn embed(&self, content: &str) -> Result<Vec<f32>>;

    /// The name of the embedding model (e.g., "text-embedding-3-small")
    fn model_name(&self) -> &str;

    /// The dimensionality of the embedding vectors
    fn dimensions(&self) -> usize;
}
```

### VectorStore Trait

Vector storage uses a pluggable adapter:

```rust
#[async_trait]
pub trait VectorStore: Send + Sync {
    /// Store an embedding vector for an entity
    async fn upsert(&self, entity_id: &str, vector: &[f32], metadata: Option<VectorMetadata>) -> Result<()>;

    /// Find the k nearest vectors to a query vector
    async fn search(&self, query: &[f32], k: usize, filter: Option<VectorFilter>) -> Result<Vec<VectorResult>>;

    /// Remove an entity's embedding
    async fn delete(&self, entity_id: &str) -> Result<()>;

    /// Rebuild the index from scratch (for derived data rebuild)
    async fn rebuild(&self) -> Result<()>;
}

pub struct VectorResult {
    pub entity_id: String,
    pub score: f64,
    pub metadata: Option<VectorMetadata>,
}

pub struct VectorFilter {
    pub entity_types: Option<Vec<EntityType>>,
    pub tags: Option<Vec<String>>,
    pub min_score: Option<f64>,
}

pub struct VectorMetadata {
    pub model: String,
    pub entity_type: String,
    pub title: String,
}
```

### Embedding Pipeline

```
Entity (with Content component)
  |
  Extract text from Content
  |
  AI Provider plugin generates embedding vector
  |
  Embedding component attached to entity
  |
  Vector stored in VectorStore
```

The pipeline runs:
- On import: new entities with Content get embeddings generated
- On content update: embeddings are regenerated
- On rebuild: all embeddings are regenerated from canonical Content components

### In-Memory Initial Implementation

The initial `VectorStore` implementation is in-memory brute-force cosine similarity:

```rust
pub struct InMemoryVectorStore {
    vectors: RwLock<HashMap<String, Vec<f32>>>,
    metadata: RwLock<HashMap<String, VectorMetadata>>,
}
```

Cosine similarity computation:

```rust
fn cosine_similarity(a: &[f32], b: &[f32]) -> f64 {
    let dot: f64 = a.iter().zip(b.iter()).map(|(x, y)| (*x as f64) * (*y as f64)).sum();
    let norm_a: f64 = a.iter().map(|x| (*x as f64).powi(2)).sum::<f64>().sqrt();
    let norm_b: f64 = b.iter().map(|x| (*x as f64).powi(2)).sum::<f64>().sqrt();
    if norm_a == 0.0 || norm_b == 0.0 { 0.0 } else { dot / (norm_a * norm_b) }
}
```

Performance: brute-force works for < 100K vectors. Beyond that, HNSW or sqlite-vec can be added as an alternative `VectorStore` implementation without changing the trait.

### Hybrid Search

Hybrid search combines BM25 (keyword) and cosine (semantic) results using Reciprocal Rank Fusion:

```rust
pub fn reciprocal_rank_fusion(
    keyword_results: &[SearchResult],
    semantic_results: &[VectorResult],
    k: usize, // RRF constant, typically 60
) -> Vec<FusedResult> {
    let mut scores: HashMap<String, f64> = HashMap::new();

    for (rank, result) in keyword_results.iter().enumerate() {
        *scores.entry(result.entity_id.clone()).or_insert(0.0) += 1.0 / (k + rank + 1) as f64;
    }
    for (rank, result) in semantic_results.iter().enumerate() {
        *scores.entry(result.entity_id.clone()).or_insert(0.0) += 1.0 / (k + rank + 1) as f64;
    }

    let mut fused: Vec<FusedResult> = scores.into_iter()
        .map(|(id, score)| FusedResult { entity_id: id, score })
        .collect();
    fused.sort_by(|a, b| b.score.partial_cmp(&a.score).unwrap());
    fused
}
```

RRF is preferred over weighted score combination because BM25 scores and cosine similarity scores are on different scales. RRF operates on ranks, which are comparable.

### Search Modes

| Mode | Behavior |
|------|----------|
| `keyword` | FTS5 BM25 search only (existing behavior) |
| `semantic` | Embedding cosine similarity only |
| `hybrid` | Both, fused via RRF |

## Alternatives Considered

### Approach 1: sqlite-vec with HNSW
- Pros: Scalable approximate nearest neighbor search, native SQLite extension.
- Cons: Adds a dependency. HNSW graph must be rebuilt on each startup (in-memory). Over-engineering for < 100K entities.
- Why not chosen: Brute-force cosine similarity is exact and fast enough for the target scale. The `VectorStore` trait is compatible with sqlite-vec when needed.

### Approach 2: External Vector Database (Qdrant, Milvus)
- Pros: Production-grade vector search, horizontal scaling, filtering.
- Cons: Violates storage independence (ADR-0002). Adds infrastructure dependency. Breaks single-binary deployment model.
- Why not chosen: Architectural principle — storage is an implementation detail. External vector databases are deployment options, not architectural requirements.

### Approach 3: Local ONNX Embeddings (all-MiniLM-L6-v2)
- Pros: No network dependency, runs entirely locally, small model (23 MB).
- Cons: Adds ONNX runtime dependency. Model quality is lower than commercial APIs. Requires Python or ONNX runtime in the build chain.
- Why not chosen: Deferred — the plugin system allows local embedders to be added as plugins without core changes.

### Approach 4: Weighted Score Fusion
- Pros: Simpler implementation, direct control over keyword vs semantic importance.
- Cons: Requires tuning weights per query type. BM25 and cosine scores are on different scales — weighting them directly produces inconsistent results.
- Why not chosen: RRF is parameter-free and more robust across different query types.

### Approach 5: Embedding Pipeline + In-Memory Cosine + RRF (chosen)
- Pros: No new infrastructure dependencies. Exact similarity search. Hybrid search improves relevance. Pluggable AI provider and vector store. Embeddings are derived data — rebuildable.
- Cons: Requires external AI provider for embedding generation (network dependency). In-memory vector store does not persist across restarts.
- Why chosen: Maximum simplicity with full semantic search capability. The plugin system allows AI providers to be swapped without core changes.

## Consequences

### Positive
- Semantic search finds conceptually related entities without exact keyword match
- Hybrid search improves relevance for queries with both exact terms and conceptual intent
- The `AiAdapter` and `VectorStore` traits are pluggable — AI providers and vector stores are swappable without core changes
- Embeddings are derived data — they can be regenerated when the embedding model changes

### Negative
- Embedding generation requires an external AI provider (network dependency or local model)
- In-memory vector store does not persist across restarts (embeddings must be regenerated)
- Embedding quality depends on the AI provider and model chosen

### Risks
- AI provider downtime blocks embedding generation. Mitigation: keyword search always works independently. Semantic search degrades gracefully.
- Embedding model changes produce different vectors. Mitigation: embeddings are versioned with the model name. Rebuild regenerates all embeddings with the new model.
