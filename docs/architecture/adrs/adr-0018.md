# ADR-0018: Collection Entity for Curated Groups

**Status:** Proposed
**Date:** 2026-07-24
**Deciders:** Core maintainers

## Context

Users need to group related entities for focused exploration. A researcher might group papers on a specific topic. A developer might group tools for a project. A curator might group entities for a knowledge base entry. Without collections, the only way to group entities is by type — but entities of different types may be related (a paper, a tool, and a concept about the same topic).

The domain model already defines `Collection` as an entity type. This ADR specifies how collections are stored, managed, and used by view projections.

## Decision

Collections are first-class entities with a many-to-many membership relationship to other entities. Collections are stored in dedicated tables and used by view projections for hierarchical navigation.

### Storage Schema

```sql
CREATE TABLE collections (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE collection_members (
    collection_id TEXT NOT NULL,
    entity_id TEXT NOT NULL,
    added_at TEXT NOT NULL,
    PRIMARY KEY (collection_id, entity_id),
    FOREIGN KEY (collection_id) REFERENCES collections(id),
    FOREIGN KEY (entity_id) REFERENCES entities(id)
);
```

### Repository Trait

```rust
#[async_trait]
pub trait CollectionRepository: Send + Sync {
    async fn create(&self, collection: Collection) -> Result<Collection>;
    async fn get(&self, id: &str) -> Result<Option<Collection>>;
    async fn update(&self, collection: Collection) -> Result<Collection>;
    async fn delete(&self, id: &str) -> Result<()>;
    async fn list(&self) -> Result<Vec<Collection>>;

    async fn add_member(&self, collection_id: &str, entity_id: &str) -> Result<()>;
    async fn remove_member(&self, collection_id: &str, entity_id: &str) -> Result<()>;
    async fn get_members(&self, collection_id: &str) -> Result<Vec<Entity>>;
    async fn get_entity_collections(&self, entity_id: &str) -> Result<Vec<Collection>>;
    async fn is_member(&self, collection_id: &str, entity_id: &str) -> Result<bool>;
}
```

### Collection Entity

```rust
pub struct Collection {

```

### CLI Commands

```bash

kos collection list

```

### Use in View Projections

Collections are used by the tree view for hierarchical grouping:

```
Knowledge Graph (Tree View)

  Collection: Papers to Read (5)
    Paper: Attention Is All You Need
    Paper: BERT: Pre-training of Deep Bidirectional Transformers
    Paper: GPT-4 Technical Report
    ...
  Concept (12)
    Self-Attention Mechanism
    Transformer Architecture
    ...
  Paper (8)
    ...
```

Collections appear as branches in the tree, containing their member entities. An entity may appear in multiple collections simultaneously — the entity is not duplicated, it is projected into each collection view.

### Events

Collections emit standard entity events through the existing event system:

| Event | Trigger |
|-------|---------|
| EntityCreated | Collection created |
| EntityUpdated | Collection title/description changed |
| EntityArchived | Collection archived |
| ComponentAdded | Entity added to collection |
| ComponentRemoved | Entity removed from collection |

### Layer Ownership

- **Layer 4 (Knowledge Model):** Collection entity and membership relationships
- **Layer 5 (Relationship Engine):** Membership queries and traversal through collections
- **Layer 6 (Derivation):** View projections that use collections for grouping

## Alternatives Considered

### Approach 1: Tags Instead of Collections
- Pros: Tags already exist. No new tables needed.
- Cons: Tags are flat labels. Collections are named, described groups with explicit membership. Different use cases — both coexist.
- Why not chosen: Collections provide curated groupings that tags cannot express.

### Approach 2: Graph Relationships for Grouping
- Pros: Uses existing relationship infrastructure. No new tables.
- Cons: `contains`/`belongs_to` relationships are semantic, not structural. Collections are structural groupings — they group entities for navigation, not for knowledge representation.
- Why not chosen: Mixing structural and semantic relationships in the same table conflates two different concerns.

### Approach 3: Virtual Collections (Saved Searches)
- Pros: No manual curation needed. Collections update automatically as entities change.
- Cons: Harder to understand and manage. Query-based membership is implicit, not explicit. Users cannot reason about what a virtual collection contains without executing the query.
- Why not chosen: Deferred to future phase. Explicit membership is simpler and more predictable.

## Consequences

### Positive
- Collections enable curated groupings independent of entity type
- The many-to-many model allows entities to appear in multiple collections
- Collections are entities themselves — they can have components, relationships, and appear in other views
- Standard event system integration — no new event types needed

### Negative
- Collection membership is manually curated — no automatic grouping (AI-assisted grouping is Year 2)
- The collection_members table adds a join for collection queries

### Risks
- Orphaned memberships (entity deleted but membership record remains). Mitigation: cascade delete on foreign key, or cleanup on entity archive.

## Test Strategy

### Unit Tests

- Collection create returns collection with correct fields
- Collection get returns existing collection
- Collection get returns None for non-existent collection
- Collection update modifies title and description
- Collection delete removes collection
- Collection list returns all collections
- add_member creates membership record
- add_member rejects duplicate membership (primary key constraint)
- remove_member deletes membership record
- get_members returns all entities in collection
- get_entity_collections returns all collections containing entity
- is_member returns true for existing membership
- is_member returns false for non-existing membership

### Integration Tests

- Collection creation emits EntityCreated event
- Adding entity to collection emits ComponentAdded event
- Removing entity from collection emits ComponentRemoved event
- Archiving collection emits EntityArchived event
- Entity in multiple collections appears in each collection's member list
- Cascade delete: archiving entity removes its collection memberships
- Tree view includes collections as branches with correct members

### Property-Based Tests

- Membership is symmetric: if A is in collection C, get_members(C) contains A
- Collection count is consistent: list().len() matches database count
- Member count is consistent: get_members(C).len() matches collection_members count for C
- Entity can belong to unlimited collections (no artificial limit)
