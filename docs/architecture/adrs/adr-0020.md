# ADR-0020: Composite Indexes for Relationship Traversal Performance

**Status:** Accepted
**Date:** 2026-07-28
**Deciders:** Core maintainers

## Context

The `relationships` table stores all typed, directed edges between entities. Every graph traversal operation — whether recursive CTE or level-by-level BFS — queries this table by `source_id`, `target_id`, or both, always with an `is_active = 1` filter to exclude soft-deleted relationships.

The current schema defines no indexes on the `relationships` table beyond the implicit primary key on `id`. This means every traversal query performs a full table scan of the entire relationships table:

- **Outgoing traversal:** `SELECT ... FROM relationships WHERE source_id = ? AND is_active = 1` — scans all rows.
- **Incoming traversal:** `SELECT ... FROM relationships WHERE target_id = ? AND is_active = 1` — scans all rows.
- **Bidirectional traversal:** Both of the above — scans all rows twice per level.

At 10K relationships, each level of traversal scans 10K rows. At the PRD-0003 target of 1M relationships and 100K entities, each level would scan 1M rows. With level-by-level BFS at depth 3 and average fan-out 10, this means approximately 1,110 full table scans of 1M rows each — over a billion row reads for a single traversal.

The `is_active` flag is present on every relationship query because soft-deleted relationships must never appear in traversal results. Indexing `source_id` or `target_id` alone would still require filtering through the table rows to check `is_active`. A composite index covering both the lookup column and the filter column enables index-only filtering: SQLite can satisfy both the equality lookup and the active check without touching the table row (a "covering index" in SQLite terms for this query pattern).

## Decision

Add two composite indexes to the `relationships` table, created at `SqliteStore::new` initialization:

```sql
CREATE INDEX IF NOT EXISTS idx_relationships_source_active
    ON relationships(source_id, is_active);

CREATE INDEX IF NOT EXISTS idx_relationships_target_active
    ON relationships(target_id, is_active);
```

### Index Design

**`idx_relationships_source_active`**: Composite on `(source_id, is_active)`.

Covers the outgoing traversal query pattern:
```sql
SELECT target_id, relationship_type
FROM relationships
WHERE source_id = ? AND is_active = 1
```

The index is ordered by `source_id` first, allowing a B-tree lookup to find all rows for a given source entity, then `is_active` second, allowing the index to skip inactive rows without reading the table. SQLite can answer this query entirely from the index if the selected columns (`target_id`, `relationship_type`) are present in the index. However, adding these extra columns would make the index wider (more pages to read) for marginal gain — the primary performance benefit is eliminating the full table scan on `source_id`.

**`idx_relationships_target_active`**: Composite on `(target_id, is_active)`.

Covers the incoming traversal query pattern symmetrically:
```sql
SELECT source_id, relationship_type
FROM relationships
WHERE target_id = ? AND is_active = 1
```

### Idempotent Creation

Indexes are created with `CREATE INDEX IF NOT EXISTS` so existing databases are upgraded automatically on next open without error or data loss.

### Why Not Single-Column Indexes

Single-column indexes on `(source_id)` and `(target_id)` separately would accelerate the equality lookup but would then require a table row lookup to check `is_active` for each candidate row. Composite indexes allow both the lookup and the filter to be satisfied within the index B-tree.

### Why Not Include `relationship_type` in the Index

The `relationship_type` filter is optional. When present, it requires a separate parameter in the `WHERE` clause. Adding `relationship_type` as a third column would create a wider index, increasing storage and B-tree depth, without commensurate benefit for the majority of traversals that do not filter by type. The `relationship_type` filter is applied as a secondary predicate on the rows returned by the index — the index already eliminated the non-matching `source_id` rows, so the remaining rows are few enough that an in-memory scan is fast.

## Alternatives Considered

### Option 1: No Indexes (current state)

- Pros: Zero storage overhead, zero write-time cost, zero migration complexity.
- Cons: Every traversal performs full table scans of the entire relationships table at every depth level. At 1M relationships and depth 3, this is over a billion row reads per traversal. Demonstrated to cause 2-hop traversal to take ~457ms at just 10K relationships.
- Why not chosen: The performance is unacceptable and fails the PRD-0003 NFR targets by multiple orders of magnitude.

### Option 2: Single-Column Indexes on `(source_id)` and `(target_id)`

- Pros: Smaller indexes than composite (one column instead of two). Accelerates the `source_id`/`target_id` equality lookup.
- Cons: After the index lookup, SQLite must fetch each matching row from the table to check `is_active`. At 10 edges/entity, this is 10 table row fetches per index lookup. The table row fetch is a random I/O operation per row. Composite indexes avoid this entirely.
- Why not chosen: The `is_active` filter is on every traversal query. Adding it to the index costs one extra byte per index entry and eliminates the table row fetch for every candidate row. The storage cost is negligible (1 byte per relationship × 1M relationships = ~1MB extra per index).

### Option 3: Composite Index with `(source_id, is_active, target_id)`

- Pros: Fully covering index — SQLite can answer the entire query from the index without touching the table at all. The `target_id` column is included as a payload column that is not part of the key but is available to the query.
- Cons: Wider index (three columns instead of two), more storage, slower bulk inserts. The `target_id` is not used for filtering — it is only returned as a result column. An index-only scan is already achieved with the two-column composite because SQLite can combine the index with the table's rowid lookup.
- Why not chosen: Marginal benefit for measurable storage and write cost. The two-column composite already eliminates the full table scan; the third column adds index width without eliminating any additional table access.

### Option 4: Composite Index with `(is_active, source_id)` (reversed order)

- Pros: All active relationships are grouped together in the index B-tree. Useful if queries frequently scan all active relationships.
- Cons: The traversal query pattern is "find all relationships for a specific source entity" — this requires scanning all entries with the same `source_id`, which is a clustered range scan. With `(is_active, source_id)` as the leading column, the B-tree would scatter relationships by `is_active` first, then by `source_id`. Finding all relationships for a given source would require scanning both the active and inactive portions of the index.
- Why not chosen: The selectivity of `source_id` (1 out of 100K) is much higher than the selectivity of `is_active` (2 out of 2 values). The leading column should be the most selective column in the query predicate.

### Option 5: Composite Indexes `(source_id, is_active)` and `(target_id, is_active)` (chosen)

- Pros: Leading column is the equality predicate (`source_id` or `target_id`). Second column enables index-only filtering on `is_active`. Eliminates full table scans from traversal queries. Indexes are created idempotently. Each index is only two columns wide.
- Cons: Storage overhead (~16 bytes per row per index at 1M relationships = ~32MB total). Write-time overhead (two index B-tree updates per relationship INSERT/UPDATE/DELETE). Migration time on large existing databases.
- Why chosen: Best balance of query acceleration, storage cost, and write overhead. Eliminates the dominant bottleneck in traversal performance (full table scans) with minimal schema change.

## Consequences

### Positive

- **Traversal queries use index seeks instead of full table scans.** `EXPLAIN QUERY PLAN` confirms `SEARCH using index idx_relationships_source_active` instead of `SCAN table relationships`.
- **Index-only filtering for `is_active`.** The composite index eliminates the need to fetch table rows to check the active flag.
- **Idempotent migration.** `CREATE INDEX IF NOT EXISTS` upgrades existing databases on open without error or data loss. No manual migration step.
- **No schema changes to canonical tables.** Indexes are storage-optimization-only. No new columns, tables, or foreign keys.

### Negative

- **Storage overhead.** Each index adds ~16 bytes per row (8 bytes for `source_id`/`target_id` TEXT, plus rowid pointer). At 1M relationships, ~32MB total for both indexes. Proportional to relationship count.
- **Write amplification.** Every relationship INSERT, UPDATE, or `is_active` toggle must update two secondary indexes. For bulk imports at 100 docs/sec with average 10 relationships/doc, this is ~2,000 index writes/second — well within SQLite's capability.
- **Migration time on large databases.** Creating indexes on a table with 1M relationships takes ~1-2 seconds. The index creation is non-blocking in WAL mode for reads but blocks writes during creation.

### Risks

- **Index creation locks database on large datasets.** On a 1M-relationship database, index creation blocks writes for ~1-2 seconds. Mitigated by running index creation at startup before accepting traffic. In practice, Knowledge OS startup already initializes the schema; adding index creation to this phase does not change the user-visible behavior.
- **Index picks wrong query plan.** In rare cases, SQLite might prefer a full table scan over an index if the statistics are stale or the query has low selectivity. Mitigated by running `ANALYZE` after index creation and verifying `EXPLAIN QUERY PLAN` in tests.
- **Storage growth surprises users on disk.** At 1M relationships, ~32MB of index storage is negligible compared to entity content (which dominates storage). Mitigated by documenting the index storage requirement in the operations guide.

## Implementation Notes

*Filed post-implementation on 2026-07-28.*

### Verification

Indexes were added to `SqliteStore::new` initialization in `store.rs`. Verification steps:
- `EXPLAIN QUERY PLAN` confirms index usage: the BFS expansion queries show `SEARCH using index idx_relationships_source_active` and `SEARCH using index idx_relationships_target_active` instead of `SCAN table relationships`.
- The indexes are created with `CREATE INDEX IF NOT EXISTS` — existing databases are upgraded automatically.
- Both `cargo test -p knowledge-storage` (81 tests) and benchmarks pass, confirming no regressions from index creation.

### Deviations

No deviations from the plan. The two composite indexes were created exactly as specified in the ADR. The index names match the plan (`idx_relationships_source_active`, `idx_relationships_target_active`).

### Benchmark Impact

With indexes in place, the BFS expansion queries perform index seeks:
- 2-hop at 1K: 4.85ms (vs ~457ms without indexes and CTE) — **99% improvement**.
- 3-hop at 1K: 6.09ms (vs ~2.8s without indexes and CTE) — **99.8% improvement**.

The composite indexes are the primary enabler of these results, reducing each BFS level's database work from a full table scan to an index seek + 10-20 row lookups.
