# ADR-0021: Tauri as Desktop Application Framework

**Status:** Accepted
**Date:** 2026-07-28
**Deciders:** Core maintainers

## Context

Knowledge OS has a fully functional CLI (`kos`) and a seven-layer pipeline (ADR-0005), but the only user interface is a terminal. The Year 1 vision (product-vision.md) calls for "a functional knowledge engine that demonstrates the core architecture" — a visual, interactive desktop application. Without this, the system remains a library, not a product.

The desktop app must meet the following requirements (PRD-0006):

- **Cross-platform:** Support macOS, Windows, and Linux from a single codebase
- **Native integration:** File dialogs, menu bar, keyboard shortcuts, window state persistence, open files in default OS applications, reveal files in OS file manager
- **Web-based UI:** Interactive views (dashboard, import, browser, detail, graph, tree, table, timeline, search) rendered in a modern webview
- **Rust backend:** Reuse existing Rust core libraries (`knowledge-core`, `knowledge-derivation`, `knowledge-import`, `knowledge-plugin`)
- **Single-binary delivery:** Users install one application, not a stack of services
- **Minimum resource usage:** Target idle memory < 50MB, comparable to a native application, not an Electron app
- **Local-first:** All data stored locally, zero cloud dependency

The pipeline architecture (pipeline.md) places the desktop app at Layer 7 (Presentation Layer). It is a consumer of lower-layer port interfaces, never a direct manipulator of canonical data.

A complete visual design system exists at `design/knowledge_os/DESIGN.md` with HTML mockups for all views in `design/`:
- `design/knowledge_os_dashboard/` — Dashboard bento-grid layout, stats cards, activity feed
- `design/entity_browser/` — Entity list with type filter, sort, and side detail panel
- `design/interactive_graph_view/` — Graph canvas with traversal controls and entity inspector
- `design/tree_view/` — Hierarchical tree with collapsible branches
- `design/table_view/` — Sortable data table with column headers
- `design/timeline_view/` — Chronological card timeline with filter controls

The design system defines color tokens (Material 3-inspired palette with custom Knowledge Blue primary), typography (Inter for UI, JetBrains Mono for data), spacing (4px grid, 260px sidebar width), shape (4px standard radius, 8px badge radius), elevation (tonal layers with minimal shadows), and component specifications (sidebar navigation, search bars, entity badges, data tables, card layouts, input fields). It supports seamless light/dark mode via system theme detection.

## Decision

Use **Tauri 2.x** as the desktop application framework. The application architecture is:

```
  Rust backend (desktop/src-tauri/)
    ├── Tauri application shell (window management, menu, dialogs)
    ├── SqliteStore (shared with CLI, Arc<Mutex<>> wrapped)
    └── Tauri IPC commands (stateless wrappers around core port traits)

  Frontend (desktop/src/)
    └── Webview (Svelte 5 + Vite + TypeScript SPA)
         ├── Tauri JS bindings (@tauri-apps/api invoke())
         ├── Views: Dashboard, Import, Browse, Detail, Graph, Tree, Table, Timeline, Search
         └── State: Svelte 5 runes module-level store
```

Tauri provides:
- A Rust backend process that runs the application logic and owns the database connection
- A webview that renders the frontend SPA (OS-native WebView — WebKit on macOS/Linux, WebView2 on Windows)
- An IPC bridge (`#[tauri::command]` → `invoke()`) for frontend-backend communication
- Plugin ecosystem: `tauri-plugin-dialog` for native file pickers, `tauri-plugin-shell` for opening files in default OS applications and revealing files in the system file manager
- Build system: `tauri build` produces native installers for all three platforms

The `SqliteStore` is held in an `Arc<Mutex<SqliteStore>>` inside `AppState`. All Tauri commands are async and acquire the lock to access the store through existing port traits (`EntityRepository`, `ComponentRepository`, `TraversalPort`, `ViewAdapter`, `SearchIndex`).

### Version Pinning

Tauri 2.11.x is pinned in `Cargo.toml`. Upgrades follow a defined schedule to mitigate the risk of API breakage between Tauri releases.

### Frontend Framework and Design System

The frontend uses **Svelte 5** (runes mode), **Vite 6**, and **TypeScript 5**. The choice follows from the Tauri architecture: any web framework works in the webview, but Svelte 5 provides the smallest bundle size of major frameworks, fine-grained reactivity via runes ($state, $derived, $effect), and no virtual DOM overhead. These properties matter for the interactive graph view where DOM updates per animation frame must be fast.

The visual design follows the specification in `design/knowledge_os/DESIGN.md`. Design tokens (colors, typography, spacing, shape) are implemented as CSS custom properties on `:root` / `.dark` selectors in `app.css`, enabling system theme detection (NF2.2) and consistent styling across all views. Each view component in `desktop/src/views/` implements the corresponding HTML mockup from the `design/` directory:

| Design Mockup | Svelte Component | Key Elements from Mockup |
|---|---|---|---|
| `design/knowledge_os_dashboard/` | `Dashboard.svelte` | Bento-grid stats cards, recent activity feed, quick actions, system health card |
| `design/entity_browser/` | `Browser.svelte` + `Detail.svelte` | Table with type badge / title / date columns, type filter dropdown, 400px detail side panel with content preview, relationships grouped by direction, source file path, "Open File" and "Show in Folder" actions |
| `design/interactive_graph_view/` | `Graph.svelte` | SVG canvas on dark dot-grid background, traversal controls (entity ID input + depth slider), entity inspector panel, zoom controls |
| `design/tree_view/` | `Tree.svelte` | Collapsible branches with connector lines, type-grouped hierarchy, active entity highlight |
| `design/table_view/` | `Table.svelte` | Sortable columns with asc/desc indicators, label-caps headers, border-bottom only rows |
| `design/timeline_view/` | `Timeline.svelte` | Vertical timeline line, entity cards with dates and type badges, filter bar, zoom grouping |

The layout model from the design system (fluid-fixed hybrid with 260px fixed sidebar) maps directly to the Svelte component structure: `App.svelte` contains the sidebar navigation and a router outlet for the main workspace. Component-level design specifications from `design/knowledge_os/DESIGN.md` (sidebar navigation patterns, entity badges, search bars, data tables, card layouts, input fields) are implemented as reusable Svelte components in `desktop/src/lib/`.

## Alternatives Considered

### Option 1: Electron

- Pros: Mature ecosystem, extensive documentation, Chrome DevTools, large community, WebSocket/Node.js native addons available.
- Cons: ~120MB base binary size, ~100-150MB baseline memory usage per process, slower build times, requires Node.js in the distribution. The memory profile violates PRD-0006 NF1.7 (< 50MB idle). The binary size is disproportionate for an application whose value is in its backend, not its shell.
- Why not chosen: Resource profile contradicts the local-first, lightweight principle. Electron's memory and disk overhead would make the app feel like a "wrapped website" rather than a native knowledge tool.

### Option 2: Wails (Go-based)

- Pros: Native Go binaries, smaller than Electron, uses OS webview, Go backend can share types with frontend via bindings.
- Cons: Requires Go backend — cannot reuse existing Rust core libraries (`knowledge-core`, `knowledge-derivation`, `knowledge-import`, `knowledge-plugin`). Rewriting the entire Rust backend in Go violates the "no implementation leakage" principle (engineering-principles.md) and would duplicate years of development. The binding system is less mature than Tauri's.
- Why not chosen: Language mismatch. The existing codebase is Rust. Porting to Go is not an option.

### Option 3: Neutralinojs

- Pros: Extremely lightweight (~2MB binary), uses OS webview, cross-platform, JavaScript/TypeScript backend possible.
- Cons: No Rust support — requires writing backend logic in JavaScript/TypeScript or Java. The backend capabilities (file system, process spawning, database access) are limited compared to Tauri's Rust backend. Cannot reuse the existing Rust port interfaces and `SqliteStore` implementation. Less mature ecosystem for native file dialogs and window management.
- Why not chosen: Cannot reuse existing Rust core. Lacks the native capability surface needed to wrap the existing pipeline layers.

### Option 4: Native Qt/GTK Application

- Pros: True native experience, full OS integration, direct access to system APIs, no webview overhead.
- Cons: Requires C++ (Qt) or C (GTK) development. Cannot reuse Rust core without FFI bridge. UI development is significantly slower than web-based SPA frameworks. Building rich interactive views (graph with D3-force, tree with expand/collapse, sortable table, timeline) requires implementing all rendering from scratch in native widgets. Cross-platform UI consistency is harder to maintain.
- Why not chosen: Development velocity is critical for the MVP (target: 8 weeks). A webview-based approach allows using mature web visualization libraries (D3-force, SVG) and reactive UI frameworks (Svelte) while keeping the backend in Rust.

### Option 5: Tauri 2.x (chosen)

- Pros: Rust backend (reuses existing codebase), OS-native webview (small binary, low memory), cross-platform from one codebase, typed IPC with `#[tauri::command]`, plugin ecosystem for native dialogs, `tauri build` produces platform installers. The `@tauri-apps/api` TypeScript bindings provide type-safe frontend-backend communication.
- Cons: Tauri 2.x is newer than Electron — smaller ecosystem, fewer community plugins, API still evolving. Webview limitations (no Chrome DevTools in production, WebView2 distribution on Windows requires the WebView2 Runtime). IPC serialization overhead on every frontend-backend call.
- Why chosen: Reuses the Rust core without FFI or language bridges. The webview approach enables fast UI iteration with modern web tools. The resource profile (estimated ~20-30MB baseline, ~5MB binary) meets all NFR targets. The IPC pattern (stateless commands wrapping port traits) preserves architectural boundaries.

## Consequences

### Positive

- **Rust backend reuse:** All existing `knowledge-core`, `knowledge-derivation`, `knowledge-import`, and `knowledge-plugin` code is used directly — no ports, no FFI, no language bridges.
- **Cross-platform from one codebase:** `tauri build` produces macOS (.app/.dmg via `tauri-plugin-dmg`), Windows (.msi), and Linux (.AppImage) installers without per-platform frontend code.
- **Small resource footprint:** OS-native WebView (no Chromium bundle) keeps binary size ~5MB and memory usage at idle under 30MB, meeting NF1.7.
- **Architectural boundary enforcement:** The IPC bridge forces developers to define explicit commands for frontend-accessible operations, preventing implementation leakage from Layer 7 to lower layers.
- **Frontend flexibility:** Any web framework works. The initial choice of Svelte 5 can be replaced without changing the backend.
- **Security model:** Tauri's capability-based security model (allowlisting IPC commands, scoped filesystem access) aligns with the principle of least privilege.

### Negative

- **IPC serialization overhead:** Every frontend-backend call serializes Rust structs to JSON and deserializes in TypeScript. For large payloads (1000-node graph), this adds ~5-20ms per call. Mitigated by pagination and depth limits in view adapters.
- **WebView limitations:** No Chrome DevTools on end-user machines. Debugging production issues requires Tauri's built-in devtools protocol or structured logging. WebView2 requires the WebView2 Runtime on Windows (pre-installed on Windows 11, downloadable on Windows 10).
- **Tauri ecosystem maturity:** Tauri 2.x plugins are fewer than Electron equivalents. If a required native capability is missing, it must be implemented as a custom Tauri plugin using Rust.
- **Single-webview architecture:** The entire UI is in one webview. A slow-rendering view (e.g., complex graph layout) can block the entire UI thread. Mitigated by Web Workers for graph layout computation.

### Risks

- **Tauri API changes between versions (PRD-0006 Risk #1):** Tauri 2.x is under active development. Future releases may break IPC command signatures, plugin APIs, or build configuration. **Mitigation:** Pin Tauri version in `Cargo.toml`. Upgrade on a defined schedule with full regression testing. Pin `@tauri-apps/api` to the matching version.
- **Cross-platform file dialog differences (PRD-0006 Risk #3):** Native file dialogs behave differently on each platform (macOS `.md` filter, Windows multi-select, Linux directory picker). **Mitigation:** Use `tauri-plugin-dialog` which abstracts platform differences.
- **Cross-platform file opening differences:** Opening files in default applications and revealing in folder differs per platform (macOS `open`, Linux `xdg-open`, Windows `explorer`). **Mitigation:** Use `tauri-plugin-shell` which normalizes these operations across platforms.
- **WebView version fragmentation:** Users on older Windows 10 builds may have an outdated WebView2 that lacks CSS features used by the frontend. **Mitigation:** Target ES2020 and CSS Grid/Flexbox — features supported by WebView2 from its initial release. Document minimum WebView2 version in system requirements.
- **Frontend bundle growth from graph library (PRD-0006 Risk #2):** D3-force adds ~20KB gzipped to the bundle. **Mitigation:** Acceptable for MVP. Defer heavy layout computation to Web Worker for large graphs.

## Related Decisions

- **ADR-0001** — Knowledge Model as Canonical Source of Truth. The desktop app consumes canonical data through port traits; it never creates or modifies canonical data directly.
- **ADR-0002** — Storage Independence via Adapter Pattern. The desktop app accesses storage through `EntityRepository`, `ComponentRepository`, `TraversalPort`, and `ViewAdapter` traits. `SqliteStore` is an adapter that can be replaced.
- **ADR-0005** — Compiler-Inspired Architecture. The seven-layer pipeline places the desktop app at Layer 7 (Presentation Layer). The IPC bridge is the Layer 7 → Layers 1–6 communication path.
- **ADR-0015** — View Projection System. The desktop app renders `ViewOutput` from existing `ViewAdapter` implementations (tree, graph, table, timeline). The Tauri IPC commands `get_tree_view`, `get_graph_view`, `get_table_view`, `get_timeline_view` call `ViewAdapter::render()`.
- **ADR-0016** — Plugin System Architecture. The desktop app accesses plugins through the capability registry. Plugin management GUI is deferred (out of scope for MVP).
- **ADR-0019** — Level-by-Level BFS for Graph Traversal. The graph view's "Explore" command calls `TraversalPort::traverse()` which uses level-by-level BFS.
- **ADR-0020** — Composite Indexes for Relationship Traversal. Graph traversal performance relies on these indexes for index-seek performance.
- **Design System** (`design/knowledge_os/DESIGN.md`) — The visual design specification that defines color tokens, typography, spacing, layout, and component patterns implemented by the frontend. HTML mockups in `design/` map directly to Svelte view components.
- **PRD-0006** — Desktop MVP PRD that specifies the functional requirements (F1–F13), NFR targets (NF1–NF2), and user stories (US1–US6).
