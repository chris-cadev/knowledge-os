# ADR-0022: Stateless Tauri IPC Bridge for Frontend-Backend Communication

**Status:** Proposed
**Date:** 2026-07-28
**Deciders:** Core maintainers

## Context

The desktop application (ADR-0021) has a split architecture: a Rust backend that owns the database connection and business logic, and a webview frontend that renders interactive views. These two halves must communicate. The frontend needs to:

- List entities with filtering and sorting
- Import files (Markdown, PDF) through the existing pipeline
- Search entities by keyword with type and tag filters
- Retrieve entity detail (components, relationships, events, versions)
- Request graph, tree, table, and timeline projections from `ViewAdapter` implementations
- Navigate the graph via `TraversalPort`

Each operation maps to an existing port trait in the core libraries. The communication layer must not duplicate business logic, must not bypass the canonical model (ADR-0001 violation), and must not leak storage or pipeline details to the frontend (engineering-principles.md question 9).

The PRD defines specific IPC commands:

```rust
// All commands follow the same pattern:
async fn command_name(
    state: tauri::State<'_, AppState>,    // shared store access
    param1: Type1,                         // typed parameters
) -> Result<ResponseType, String> {       // typed response
    let store = state.store.lock()...;
    // call one or more port trait methods
    // map to response type
    Ok(response)
}
```

The engineering questions (PRD-0006 §Engineering Questions) confirm: the desktop app is a renderer of canonical and derived data. It introduces no new entities, relationships, components, or events. It must not violate storage independence (question 8) or introduce implementation leakage (question 9).

## Decision

We adopt a **stateless Tauri IPC bridge** pattern where:

1. **Each frontend capability is a single `#[tauri::command]` function.** No command depends on session state, authentication state, or prior commands.

2. **Each command is a thin wrapper** — it acquires a lock on `AppState.store`, calls one or more existing port trait methods, maps the output to a serializable response type, and returns. No business logic lives in commands.

3. **Response types are defined per command** — minimal serializable structs that carry only the data the frontend needs. They are not the canonical entity/component/relationship types — they are view-specific projections.

4. **Error handling returns `Result<T, String>`** — typed errors on the Rust side are converted to error messages. The frontend receives `{ error: string }` and displays it. This is a deliberate simplification for MVP; structured error types can be introduced later.

5. **Commands are async** — long-running operations (import, graph traversal at scale) run asynchronously and return a future. Tauri manages the async runtime.

6. **AppState holds a single `Arc<Mutex<SqliteStore>>`** — all commands share the same database connection through the mutex. This is safe because the desktop app is single-process with no concurrent CLI access (documented limitation).

### IPC Command Catalog

| Command | Port Trait(s) Used | Response Type |
|---|---|---|
| `list_entities` | `EntityRepository::find_by_type`, `EntityRepository::list`, `ComponentRepository::get` | `Vec<EntitySummary>` |
| `import_files` | Import pipeline (from `knowledge-import`) | `ImportResult` |
| `search_entities` | `SearchIndex::search` | `Vec<SearchResult>` |
| `get_entity_detail` | `EntityRepository::find_by_id`, `ComponentRepository::get`, `RelationshipRepository::get`, event log query, version history query | `EntityDetail` |
| `get_graph_view` | `GraphViewAdapter::render` (which internally uses `TraversalPort::traverse`) | `GraphOutput` |
| `get_tree_view` | `TreeViewAdapter::render` | `TreeOutput` |
| `get_table_view` | `TableViewAdapter::render` | `TableOutput` |
| `get_timeline_view` | `TimelineViewAdapter::render` | `TimelineOutput` |

### Thin Wrapper Principle

Each command must be verifiable as a thin wrapper by inspection. The implementation follows this structure:

```
1. Lock state.store
2. Call 1-3 existing port methods (no new queries)
3. Map canonical types to response types (field selection, renaming)
4. Return response or error string
```

If a command needs a query that does not exist as a port method, the port trait is extended — not implemented inline in the command. This preserves the adapter pattern and keeps the IPC layer thin.

### No Stateful Service Layer

There is no intermediate service layer between commands and port traits. The commands call port methods directly. This is appropriate because:

- Commands are stateless — no session to manage
- Each command maps to exactly one user intent (list entities, get detail, import files)
- The port traits already encapsulate the business logic at the right granularity
- Adding a service layer would duplicate the trait dispatch logic without adding abstraction value

### Frontend Binding

On the frontend, each command is wrapped in a typed TypeScript function:

```typescript
// lib/api.ts
import { invoke } from '@tauri-apps/api/core';

export async function listEntities(entityType?: string): Promise<EntitySummary[]> {
  return invoke('list_entities', { entityType });
}

export async function getEntityDetail(id: string): Promise<EntityDetail> {
  return invoke('get_entity_detail', { id });
}
// ... etc
```

The `invoke` function handles serialization (TypeScript → JSON → Rust), IPC transport, and deserialization (Rust → JSON → TypeScript). TypeScript interfaces in `lib/types.ts` mirror the Rust response types and are manually kept in sync (no code generation for MVP).

## Alternatives Considered

### Option 1: Embedded HTTP Server (actix-web/axum in a background thread)

- Pros: Standard REST API — any HTTP client can access backend capabilities. Enables future programmatic API access. Clear request/response cycle with standard status codes. Easy to test with curl/Postman.
- Cons: Requires binding a port, managing TLS (for localhost security), handling CORS, and running a separate HTTP runtime alongside Tauri's async runtime. HTTP overhead (headers, serialization, connection management) on every call. Bypasses Tauri's IPC security model (capability allowlisting). Every command must be implemented as both a Tauri command and an HTTP endpoint, or the backend must choose one communication channel and ignore the other.
- Why not chosen: Adds infrastructure complexity for no benefit in the single-user desktop context. Tauri IPC already provides typed, secure, local communication. The REST API can be added later as a separate capability (e.g., for headless operation or MCP server) — it does not need to be the primary frontend-backend channel.

### Option 2: gRPC / FlatBuffers for Binary IPC

- Pros: Binary serialization (smaller payloads, faster parsing than JSON), schema-defined contracts with code generation, streaming support for real-time graph updates.
- Cons: Requires protoc/flatc build toolchain, code generation step, gRPC runtime in both Rust and TypeScript. Adds significant build complexity for MVP. Tauri IPC already uses JSON over stdin/stdout (in dev) or a custom protocol (in production) — replacing this with gRPC requires bypassing Tauri's built-in communication.
- Why not chosen: Over-engineered for MVP. JSON serialization via serde is fast enough for the expected payload sizes (< 1MB per response). Code generation adds build complexity that delays the 8-week timeline. Streaming can be added later using Tauri events if needed.

### Option 3: Direct Object Reference (pass Rust objects to frontend)

- Pros: Zero serialization overhead — frontend accesses Rust objects directly. No IPC boundary.
- Cons: Technically impossible in Tauri's architecture (webview is separate process, memory isolation). Would require a custom in-process webview or embedding V8 with Rust bindings. Violates the process isolation that makes Tauri secure.
- Why not chosen: Not feasible with Tauri's architecture. The IPC boundary is a feature, not a limitation — it enforces the architectural separation between Layer 7 and lower layers.

### Option 4: Event-Driven Communication (Tauri events for all data flow)

- Pros: Decoupled frontend-backend communication. Backend can push updates (import progress, real-time graph changes). Frontend subscribes to events rather than calling commands.
- Cons: Loss of request-response correlation (every event needs a correlation ID for response matching). More complex error handling (events can be missed). Imperative operations (import, search) map poorly to event-driven patterns — they are inherently request-response. View rendering becomes harder to reason about when data arrives asynchronously through multiple event streams.
- Why not chosen: The IPC commands are request-response operations — the user clicks a button and expects a result. Event-driven communication is appropriate for push notifications (import progress, derivation updates) and can be added alongside commands for that purpose. It does not replace the command pattern.

### Option 5: Stateless Tauri IPC Commands (chosen)

- Pros: No session state, typed parameters and responses, async execution, Tauri-managed IPC transport, thin wrappers around tested core code, no business logic duplication. Commands are individually testable with `cargo test`. The pattern is simple enough that each command is ~20-50 lines of Rust code.
- Cons: JSON serialization overhead on every call. No streaming support (each command returns a single response). No push capability — the frontend must poll or the backend must use Tauri events separately. Manually maintained TypeScript type definitions can drift from Rust types.
- Why chosen: Minimum infrastructure for maximum clarity. The pattern directly maps frontend actions to backend capabilities. Tauri manages the transport, serialization, and async execution. The thin wrapper constraint ensures architectural boundaries are preserved.

## Consequences

### Positive

- **No business logic duplication:** Every command delegates to existing port traits. New capabilities require either a new port method or wiring an existing one — not implementing logic in the command.
- **Testable commands:** Each command can be unit-tested with a mock `SqliteStore`. The thin wrapper pattern makes commands simple enough that tests focus on parameter mapping and error handling, not business logic.
- **Clear API surface:** The eight commands define the complete frontend-accessible API. Adding a new command requires a deliberate addition to `commands.rs`, `lib.rs` (Tauri registration), and `lib/api.ts`.
- **Storage independence preserved:** Commands access storage through port traits, not through direct SQL. Replacing `SqliteStore` with a different adapter requires no command changes.
- **Async by default:** Long-running operations (import, graph traversal on 100K entities) do not block the UI. Tauri's async commands allow the frontend to show progress indicators while the backend processes.
- **Type safety:** Rust's type system validates command inputs before they reach the frontend. TypeScript interfaces provide compile-time checking on the frontend side.

### Negative

- **JSON serialization overhead:** Every command round-trips through serde JSON serialization/deserialization. For a 1000-node graph output, this adds ~5-15ms per call. Acceptable for MVP targets (NF1.4: graph view load < 1s, NF1.6: entity detail < 200ms).
- **Manual type synchronization:** TypeScript interfaces in `lib/types.ts` must be manually kept in sync with Rust response types. A mismatch causes runtime errors (silent `undefined` fields or type coercion bugs). **Mitigation:** Integration tests that verify each command's response can be deserialized into the corresponding TypeScript interface. Long-term: code generation from Rust types to TypeScript.
- **String error types:** Returning `Result<T, String>` loses structured error information. The frontend receives only a message string, not an error code or recovery hint. **Mitigation:** Acceptable for MVP. Structured error types can be introduced in a future PRD by defining an `ApiError` enum serializable to both Rust and TypeScript.
- **No built-in push mechanism:** The frontend cannot receive real-time updates (import progress, derivation events) through commands. **Mitigation:** Use Tauri events (`emit()` / `listen()`) for push notifications alongside commands for request-response operations.

### Risks

- **Command surface grows without structure:** As the desktop app evolves, the number of IPC commands may grow without clear organization, leading to a flat namespace of 50+ commands. **Mitigation:** Commands are grouped by capability domain (entity, import, search, view). If commands exceed ~20, introduce submodules in `commands/` directory.
- **Arc<Mutex<>> contention:** If multiple commands execute concurrently (e.g., search while import is running), they contend on the same mutex lock. **Mitigation:** Tauri commands are async and the lock is held briefly for each call. Import commands can be structured to acquire the lock only for checkpoint writes, not for the entire file processing pipeline.
- **Serialization performance at scale:** Entity detail for entities with 100+ components or 1000+ relationships produces a large JSON payload. **Mitigation:** Paginate relationships and events in the response. The `EntityDetail` response includes only the first 50 relationships and 50 events by default, with optional pagination parameters.
- **Type drift between Rust and TypeScript:** A Rust field rename without updating the TypeScript interface causes silent undefined values in the frontend. **Mitigation:** Add a CI step that verifies the TypeScript types against the Rust response structs using a schema comparison script.

## Related Decisions

- **ADR-0021** — Tauri as Desktop Application Framework. The IPC bridge is the communication mechanism enabled by Tauri. The command pattern is built on `#[tauri::command]` and `@tauri-apps/api/core::invoke()`.
- **ADR-0001** — Knowledge Model as Canonical Source of Truth. Commands wrap port traits that read the canonical model. No command bypasses the canonical model to access storage directly.
- **ADR-0002** — Storage Independence via Adapter Pattern. Commands access storage through port trait abstractions. The `AppState.store` is an `Arc<Mutex<dyn Store>>` — any storage adapter can be substituted.
- **ADR-0015** — View Projection System. The four view commands (`get_graph_view`, `get_tree_view`, `get_table_view`, `get_timeline_view`) call `ViewAdapter::render()`, which is the Layer 6 derivation API. The command is the Layer 7 entry point.
- **ADR-0004** — Event-Driven Derivation Pipeline. Import commands emit events through the existing pipeline. The IPC bridge does not introduce new event types; it invokes existing import operations that already emit events.
