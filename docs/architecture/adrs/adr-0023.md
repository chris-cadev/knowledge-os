# ADR-0023: ChatCompletion Port Trait for LLM Provider Abstraction

**Status:** Proposed
**Date:** 2026-07-29
**Deciders:** Core maintainers

## Context

The chat feature in PRD-0007 lets users converse with their knowledge graph through natural language. The system must integrate with multiple Large Language Model providers: OpenAI (GPT-4o), any OpenAI-compatible endpoint (LM Studio, vLLM, llama.cpp server, Together AI, Groq), Ollama (local models), and a Mock provider for testing and offline use.

The architecture documents establish that AI is a system component (`docs/architecture/ai.md`) and that the domain model must remain free of implementation details. The existing import layer follows this pattern through `ImportAdapter` (ADR-0007): a port trait in `knowledge-core` with concrete adapters per format. Storage independence (ADR-0002) follows the same principle.

The chat pipeline must:
- Accept a structured request (system prompt, message history, entity context, response mode, source toggles, configuration).
- Return either a complete response or a streaming sequence of deltas.
- Allow runtime provider selection through configuration (KOS_CHAT_PROVIDER, OPENAI_API_KEY, KOS_OPENAI_BASE_URL, OLLAMA_HOST).
- Isolate provider-specific concerns (HTTP endpoints, authentication, SSE formats, error mapping) behind a single interface.
- Allow future use from any Rust context: Tauri IPC commands, a future REST API, a future Model Context Protocol server.

Without a port trait, provider details leak into the domain model and the chat pipeline. Adding a new provider requires modifying the pipeline. Testing the pipeline requires a live network connection. The system cannot degrade gracefully to a mock when no provider is configured.

## Decision

A new `ChatCompletion` port trait is added to `knowledge-core/src/ports/chat.rs`. The trait defines the chat provider contract. Concrete adapters implement the trait for each supported provider. The chat pipeline depends on `Box<dyn ChatCompletion>`, never on a concrete provider.

```rust
#[async_trait]
pub trait ChatCompletion: Send + Sync {
    /// Send a chat request and receive a complete response.
    async fn chat(&self, request: ChatRequest) -> Result<ChatResponse, ChatError>;

    /// Send a chat request and receive a streaming response.
    async fn chat_stream(
        &self,
        request: ChatRequest,
    ) -> Result<Box<dyn Stream<Item = ChatDelta> + Send + Unpin>, ChatError>;
}
```

All request and response types (`ChatRequest`, `ChatResponse`, `ChatDelta`, `Message`, `MessageRole`, `EntityContext`, `CitationSource`, `ResponseMode`, `SourceToggles`, `ResponseFeedback`, `ChatConfig`, `ProcessingStatus`, `ChatError`) are defined in `knowledge-core` and derive `Serialize`/`Deserialize`. They have no provider-specific fields. Provider configuration is held inside each adapter, not in the request type.

The initial adapters are built-in (not plugin-routed):
- **OpenAiChatAdapter** — calls `POST {base_url}/chat/completions`. Default `base_url` is `https://api.openai.com/v1`. Configurable to any OpenAI-compatible endpoint.
- **OllamaChatAdapter** — calls `POST {endpoint}/api/chat`. Default `endpoint` is `http://localhost:11434`. Configurable to remote Ollama hosts.
- **MockChatAdapter** — deterministic echo of provided entity context. Returns canned responses. Zero network dependency.

Adapter selection is governed by a `create_chat_provider(config: &str) -> Result<Box<dyn ChatCompletion>, ChatError>` factory function. The factory parses a configuration string and returns the appropriate adapter. The factory is the only place where provider-specific construction logic lives.

Provider configuration is persisted through the existing application state mechanism. Connection test (`chat_test_provider`) is a separate operation that verifies reachability and returns latency. The Mock adapter is the default when no provider is configured, so chat works offline and during evaluation.

The trait is *not* registered as a plugin capability in the initial release. Chat adapters are built-in for launch (PRD-0007 explicitly defers plugin-based chat providers). The plugin extension point remains available for future phases through ADR-0016's capability registry without modifying this trait.

## Alternatives Considered

### Option 1: Direct provider integration in the chat pipeline

- Pros: No new abstraction. Direct call to OpenAI or Ollama from the pipeline. Simple, minimal code.
- Cons: Provider details (HTTP endpoints, JSON schemas, SSE parsing, error codes) leak into the pipeline. Adding a new provider requires modifying the pipeline. The pipeline is tightly coupled to network state — testing requires a live connection. The system cannot fall back to a mock without conditional branches scattered through the pipeline. Future MCP server or REST API must re-implement provider dispatch.
- Why not chosen: Violates the adapter pattern established by ADR-0002 and ADR-0007. Couples the domain model to specific AI providers. Prevents the framework-agnostic service layer required by F5.1.

### Option 2: One trait per provider (OpenAiCompletion, OllamaCompletion, ...)

- Pros: Each provider has a minimal interface. No general request type — each provider defines its own request shape.
- Cons: The chat pipeline must know every provider type. Adding a new provider changes the pipeline. Type explosion in the pipeline. Dynamic dispatch over multiple unrelated traits requires an enum or trait object wrapper anyway.
- Why not chosen: The providers are conceptually the same capability (chat completion). Splitting the trait per provider does not model the actual relationship. The pipeline gains no flexibility from the split — it still needs a unified request type to retrieve context, build the system prompt, and call the provider.

### Option 3: LangChain-style abstraction framework

- Pros: Mature ecosystem. Pre-built integrations for many providers. Standardized "Chain" and "PromptTemplate" abstractions.
- Cons: External dependency on a heavy framework that imposes its own abstractions. LangChain's abstractions (Chains, Agents, Tools) are oriented toward general LLM orchestration, not knowledge-graph-bound RAG. The framework's data model conflicts with the canonical entity model. A dependency on a fast-moving external project increases long-term maintenance risk. The Rust ecosystem does not have a LangChain equivalent with comparable maturity.
- Why not chosen: External framework adoption is incompatible with the "AI is a system component" principle. The system already has its own RAG pipeline (search index, vector store, entity retrieval). A framework that provides generic orchestration adds a parallel abstraction layer for no architectural benefit.

### Option 4: ChatCompletion port trait with built-in adapters (chosen)

- Pros: Mirrors the `ImportAdapter` pattern (ADR-0007) for consistency. Single trait covers all providers. Mock adapter enables testing and offline use without conditional branches. All request/response types are serializable, enabling future MCP and REST exposure. Provider selection is a configuration concern, not a code change. Plugin extension remains available for future phases without modifying the trait.
- Cons: Adds a trait abstraction with associated types and error variants. The trait may need refinement as new providers expose provider-specific features (function calling, structured output, vision input). The factory function (`create_chat_provider`) is a small dispatch surface that must be updated for new built-in providers.
- Why chosen: Consistent with the established adapter pattern. The trait is the minimum interface that captures all provider capabilities needed today. Built-in adapters (not plugins) match PRD-0007's launch scope. The serializable types enable MCP compatibility (ADR-0028) and the future REST API.

## Consequences

### Positive

- **AI provider independence:** The chat pipeline depends on `Box<dyn ChatCompletion>`. Any provider implementing the trait can be substituted. Replacing OpenAI with a self-hosted model requires only a new adapter.
- **Testable pipeline:** The MockChatAdapter enables deterministic unit tests of the chat pipeline. No network calls in tests. Test outcomes are reproducible.
- **Offline-first:** When no provider is configured, the Mock adapter is the default. The chat view works for evaluation, demo, and development without API keys or network access.
- **Framework-agnostic service layer:** The `ChatPipeline` is a standalone struct that can be invoked from Tauri commands, a future REST API, or a future MCP server. No coupling to the desktop framework (ADR-0021, ADR-0022).
- **Consistent adapter pattern:** Mirrors `ImportAdapter` (ADR-0007), `VectorStore` (ADR-0017), and `ViewAdapter` (ADR-0015). Engineers familiar with one adapter pattern understand all.
- **Serializable contracts:** All request and response types derive `Serialize`/`Deserialize`. The trait is consumable from any transport that supports JSON — Tauri IPC, REST, MCP, gRPC.

### Negative

- **Trait surface area may grow:** As new providers expose new features (function calling, vision input, structured output), the trait may need new methods or new request fields. Each addition requires updating all adapters.
- **Provider configuration is a separate concern:** The factory function (`create_chat_provider`) parses configuration strings and instantiates adapters. Misconfiguration produces runtime errors, not compile-time errors. A schema for provider configuration is required to validate setup before first use.
- **No plugin routing at launch:** Chat providers are built-in. Community providers require modifying the factory. Deferred per PRD-0007's launch scope but limits extensibility in the initial release.
- **Mock adapter can mask real provider issues:** Tests that pass with the mock may fail against a real provider. Mitigation: integration tests against a real OpenAI-compatible endpoint (e.g., LM Studio at `http://localhost:1234/v1`) in the CI environment.

### Risks

- **Provider API changes:** OpenAI and Ollama APIs may change. The `OpenAiChatAdapter` is version-pinned and the request body follows a documented schema. If the schema changes, only the adapter needs updating, not the pipeline.
- **Streaming protocol differences:** SSE formats differ between OpenAI (`data: {...}\n\n`) and Ollama (newline-delimited JSON). Each adapter handles its own protocol. The `ChatDelta` type abstracts this so the consumer sees uniform deltas.
- **Connection failures during chat:** A network failure mid-stream produces a partial response. The `ChatError` enum includes `Network`, `Provider`, `RateLimited`, and `ContextTooLong` variants. The frontend displays errors with retry options. The conversation is preserved with the partial response (per F2.19 stop-generation behavior).
- **Sensitive data in chat messages:** Cloud providers (OpenAI) receive the user's knowledge context and conversation content. The risk is documented in the security model. The Ollama adapter provides a local-only path. A warning is displayed when a cloud provider is selected for the first time.
- **Hallucination from entity context:** LLMs may fabricate facts not present in the provided entity context. The system prompt strictly constrains responses (citation required, "I don't have that information" when context is missing). Confidence scores for citations are a future enhancement.

## Related Decisions

- **ADR-0002:** Storage Independence via Adapter Pattern — the `ChatCompletion` trait extends the adapter pattern to AI providers.
- **ADR-0007:** Multi-Format Import via ImportAdapter Trait — establishes the trait-based adapter pattern that this ADR follows.
- **ADR-0016:** Plugin System Architecture — chat providers are built-in at launch, not routed through the capability registry. Plugin-based chat providers are a future phase.
- **ADR-0017:** Semantic Search via Embeddings — establishes the `AiAdapter` trait for embedding generation. `ChatCompletion` is a parallel trait for chat completion, not a generalization of `AiAdapter`.
- **ADR-0021:** Tauri as Desktop Application Framework — the chat pipeline is invoked from Tauri IPC commands (`chat_send`, `chat_stream`).
- **ADR-0022:** Stateless Tauri IPC Bridge — the IPC commands are thin wrappers that call `ChatPipeline::chat()` and `ChatPipeline::chat_stream()`. The pipeline itself is framework-agnostic.
- **ADR-0025:** Chat Context Assembly as a Derivation Layer Pipeline — the system prompt is assembled by the derivation layer and passed to the `ChatCompletion` trait.
- **ADR-0028:** MCP-Compatible Service Architecture — the serializable types and framework-agnostic pipeline enable future MCP exposure.
