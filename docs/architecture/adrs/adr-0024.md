# ADR-0024: Conversation and Message as Canonical Entities

**Status:** Proposed
**Date:** 2026-07-29
**Deciders:** Core maintainers

## Context

The chat feature in PRD-0007 introduces conversational access to the knowledge graph. Users ask questions, the system retrieves context, and the LLM produces a grounded response. The exchange must persist: users expect conversation history, the ability to rename and delete conversations, and the ability to revisit prior reasoning.

Two architectural patterns are possible:

1. **Side-table approach.** Conversations and messages live in a dedicated table outside the entity model. The chat feature bypasses the canonical model. The knowledge graph and the chat history are two separate stores with two separate query languages.

2. **Canonical entity approach.** Conversations and messages are first-class entities. They are created, versioned, archived, and queried through the same storage, event, and retrieval mechanisms as Papers, Concepts, and People.

The architecture documents (philosophy.md, data-model.md, domain-model.md) establish the second pattern as the foundational principle. ADR-0001 declares the knowledge model the source of truth. ADR-0003 introduces the entity component model for all knowledge. The system has no special-case storage for any feature. AI context, search, and graph traversal all operate on canonical entities. Chat must follow the same pattern or it introduces a parallel system that drifts from the architecture.

Beyond consistency, the canonical approach enables graph queries over conversation history: "What papers were discussed in conversations about transformers?" is a graph query that joins Conversation entities to Paper entities through `references` relationships. The side-table approach cannot answer this question without custom integration code.

The chat also produces intermediate artifacts (the system prompt sent to the LLM, the AI's draft response) that must be clearly separated from the canonical conversation. The architecture distinguishes canonical data (cannot be recreated) from derived data (regenerable, disposable). Conversation content is canonical. The system prompt and embedding vectors for semantic chat search are derived.

## Decision

Two new entity types are added to the canonical model: `Conversation` and `Message`. They follow the same rules as all existing entity types (Concept, Person, Paper, etc.) — exactly one type, type never changes, extensible through configuration.

```text
Conversation
  A series of messages between user and AI
  Example: "Q3 research review", "Onboarding chat"

Message
  A single turn in a conversation
  Example: A user question or an AI response
```

Two new component types are added:

```text
MessageContent
  Payload: { role: "user" | "assistant" | "system", text: string }
  Description: The text content of a message
  Required for: every Message entity

EntityRefs
  Payload: { entity_ids: Uuid[] }
  Description: Entity references pinned as context for this message
  Optional: only present when the message references knowledge entities
```

Three new relationship types are added:

```text
has_message
  Source: Conversation
  Target: Message
  Description: A conversation contains this message

part_of
  Source: Message
  Target: Conversation
  Description: This message belongs to the conversation
  (part_of already exists for generic entity membership; this entry formalizes the
   Conversation-Message direction)

referenced_by
  Source: Any entity
  Target: Message
  Description: The entity is referenced by this message
```

The `referenced_by` relationship is the inverse direction of the existing `references` type. It enables queries in the form "what messages reference this entity?" without requiring a full graph traversal from the entity. The relationship is additive: existing `references` relationships are unchanged.

Four new events are emitted:

```text
ConversationCreated        canonical   A new Conversation entity is created
MessageCreated             canonical   A Message is persisted to a conversation
EntityReferenced           canonical   An entity is mentioned via @-mention
ChatContextRetrieved       derivation  Entities were fetched for RAG context
```

The first three follow the existing canonical event structure (EntityCreated-family with `entity_id`, `timestamp`, `version`, `metadata`). `ChatContextRetrieved` is a derivation event — it signals that the derivation layer assembled a system prompt from canonical entities, but it carries no canonical data itself.

Conversations are persisted through the existing `EntityRepository`, `ComponentRepository`, and `RelationshipRepository` port traits (ADR-0002). No new storage paths are introduced. Conversations survive app restarts because they are canonical entities stored in the same database as Papers and Concepts.

Listing conversations (`chat_list_conversations`) is a query against `EntityRepository::find_by_type(EntityType::Conversation)`. Renaming a conversation is a `ComponentRepository::update` on the `Title` component. Deleting a conversation is `EntityRepository::archive` — never a hard delete (ADR-0001: entities are never hard-deleted).

The chat pipeline (`ChatPipeline::chat()`) is responsible for:
1. Loading or creating the `Conversation` entity.
2. Persisting the user's `Message` with role `user` and the `EntityRefs` component populated from the `@`-mentions.
3. Calling `ChatCompletion::chat()` or `chat_stream()` with the assembled context (see ADR-0025).
4. Persisting the AI's `Message` with role `assistant` and the `EntityRefs` component populated from any entities the LLM cited.
5. Creating the `has_message` and `referenced_by` relationships.

## Alternatives Considered

### Option 1: Side-table storage for conversations

- Pros: Chat-specific schema optimized for conversation patterns (ordered by time, indexed by user, paginated). No need to extend the entity model. Chat storage is independent of canonical storage and can be scaled or replaced separately.
- Cons: Two storage systems for one product. Conversation history cannot be searched by the standard `SearchIndex` or traversed by the graph engine. AI cannot reason over past conversations unless the chat module explicitly integrates with the canonical layer. The chat becomes a feature bolted on top of the system, not part of the system. Violates ADR-0001 — the knowledge model is no longer the complete source of truth.
- Why not chosen: Architectural inconsistency. The chat becomes a second-class citizen of the system. Cross-feature queries (e.g., "what conversations mentioned this paper?") require custom integration code that does not generalize.

### Option 2: Single "ChatLog" entity with all messages inline

- Pros: One entity per conversation. Simpler relationship structure. The conversation is a single canonical record.
- Cons: The `Content` component must store the entire message history as a single Markdown document. Granular queries (e.g., "find the message that cited this paper") require parsing the document. Individual messages cannot be versioned independently. Citations and `EntityRefs` are at the document level, not the message level — losing the ability to track which specific message referenced an entity. Large conversations produce entities with very large `Content` payloads.
- Why not chosen: Granularity matters. The engineering principle is that every meaningful concept is an entity. A message is a meaningful concept. Collapsing messages into a single document loses the unit of versioning, citation, and reference.

### Option 3: Conversations as derived data (regenerable from event log)

- Pros: Conversation history could be replayed from the event log. No canonical storage for chat. Frees the entity model from chat-specific types.
- Cons: Conversation content is not regenerable. The actual words exchanged between user and AI are unique and cannot be reconstructed from any other source. Per ADR-0001 and data-model.md, only data that *can* be regenerated is derived. The event log captures the change, not the message. Conversation content is canonical by the definition in data-model.md.
- Why not chosen: Misclassifies canonical data as derived. Violates ADR-0001 and the data-model invariants.

### Option 4: Conversation and Message as canonical entities with typed components and relationships (chosen)

- Pros: Follows the established entity component model (ADR-0003). Storage independence is preserved (no new storage paths). Graph queries work over conversation history (e.g., "conversations that cited this paper"). Per-message versioning and citation tracking. Events are consistent with the existing canonical event structure. The chat is a first-class citizen of the system, not a side feature.
- Cons: The domain model grows with two new entity types, two new component types, and three new relationship types. Every layer that processes entities must handle the new types. The chat pipeline is responsible for creating the correct relationship graph.
- Why chosen: Architectural consistency. The chat becomes part of the knowledge graph, not a separate system. The system can answer questions about its own conversation history through the same query mechanisms it uses for any other entity.

## Consequences

### Positive

- **Conversations are first-class knowledge.** The chat history is part of the knowledge graph. Users can search past conversations, traverse the conversation graph, and ask the AI to reason over prior exchanges.
- **Granular citation tracking.** Each message has its own `EntityRefs` component. The system can identify which specific message cited which entity. Future features (citation statistics, "most-cited papers in your conversations") are graph queries.
- **Versioning and auditability apply uniformly.** Conversation edits, renames, and deletions produce versioned events in the same stream as other entity changes.
- **No new storage path.** Conversations use the existing `EntityRepository`, `ComponentRepository`, and `RelationshipRepository`. The plugin system (ADR-0016) and storage adapters (ADR-0002) work for conversations without modification.
- **Cross-feature queries are native.** "What conversations mentioned this paper?" is a graph query over `referenced_by` relationships. "What did the AI say about this concept?" traverses from Concept → Message via `referenced_by` then filters by `MessageContent.role = "assistant"`.
- **Search includes conversations.** The derivation layer's `SearchIndex` includes `MessageContent.text` in the inverted index. Users can search their conversation history through the same search interface used for Papers and Concepts.
- **Conversation events drive derivation.** The new `ConversationCreated`, `MessageCreated`, and `EntityReferenced` events feed the event-driven derivation pipeline (ADR-0004). Embeddings for messages are generated automatically. Cache invalidation works without special-casing chat.

### Negative

- **Domain model expansion.** Two new entity types, two new component types, three new relationship types, four new events. The domain model documentation grows. Every layer that enumerates types must handle the new entries.
- **Conversation storage grows over time.** Long-lived users accumulate many conversations. The `EntityRepository` and search index must handle the volume. The event log grows correspondingly. Periodic archival of old conversations is a future operational concern.
- **Granular event volume.** Every message produces a `MessageCreated` event plus per-reference `EntityReferenced` events. A 20-message conversation with 3 references per message produces 80 events. The event-driven pipeline must handle this volume efficiently.
- **Chat UI must implement entity semantics.** The chat view must call existing port methods (`EntityRepository::create`, `ComponentRepository::add`, `RelationshipRepository::create`) rather than a chat-specific API. This is consistent with the architecture but requires the chat view to understand the entity model.
- **No chat-specific query optimizations.** Side-table storage could optimize for chat patterns (e.g., pagination by recency). The entity query interface is general-purpose. Performance is acceptable for the target scale (F2.2) but may require future indexes on `entity_type = "Conversation"` if conversation count grows large.

### Risks

- **Conversation archival policy:** Users may want to delete old conversations. Hard delete is forbidden (ADR-0001). Archive marks the entity inactive. Future PRD may add a "purge archived conversations after N days" feature that is explicitly opt-in.
- **Cross-conversation citation inflation:** A single entity referenced by many messages produces many `EntityRefs` entries and `referenced_by` relationships. The graph storage must handle this. The `EntityRefs` component is a list on the Message side; the `referenced_by` relationships are edges on the entity side. Both must be consistent.
- **Embedding generation for conversations:** Semantic search over conversation history requires embeddings for every message. The embedding pipeline (ADR-0017) processes `MessageContent` like any other content component. The cost scales with message count. A toggle to exclude old conversations from embedding generation is a future operational concern.
- **Privacy of conversation content:** Conversations may contain sensitive information. The `Provenance` component on the `Conversation` entity tracks the source (e.g., "created via chat view in user session"). The `Permissions` component can be extended to restrict access. Standard security practices apply.
- **Conversation listing performance:** `chat_list_conversations` queries `EntityRepository::find_by_type(EntityType::Conversation)` and reads the most recent `Message` for each. As conversation count grows, the query may need an index on `entity_type + updated_at`. The SQL pattern in PRD-0007 (§"SQL Patterns for Entity Autocomplete") is the baseline.

## Related Decisions

- **ADR-0001:** Knowledge Model as Canonical Source of Truth — conversations are canonical.
- **ADR-0003:** Entity Component Model for Knowledge Entities — Message and Conversation follow the same component model as all other entities.
- **ADR-0004:** Event-Driven Derivation Pipeline — `ConversationCreated`, `MessageCreated`, and `EntityReferenced` feed the event system. Embeddings for messages are generated through the same pipeline.
- **ADR-0017:** Semantic Search via Embeddings — `MessageContent` is indexed and embedded like any other content component. Semantic search includes conversations.
- **ADR-0023:** ChatCompletion Port Trait for LLM Provider Abstraction — the chat pipeline uses the `ChatCompletion` trait to obtain AI responses. The pipeline is responsible for persisting the response as a `Message` entity.
- **ADR-0025:** Chat Context Assembly as a Derivation Layer Pipeline — the system prompt is assembled from canonical entities, then passed to `ChatCompletion::chat()`. The resulting `Message` is canonical.
