# ADR-0026: Pluggable OCR Backend Trait with Image Blobs as Canonical and OCR Text as Derived

**Status:** Proposed
**Date:** 2026-07-29
**Deciders:** Core maintainers

## Context

Universal import (PRD-0007) accepts documents from many formats, including formats where text is embedded in images: scanned PDFs, office documents with embedded images (charts, screenshots, photos of whiteboards), and standalone image files (PNG, JPG, GIF, BMP). To extract text from these images, the system needs Optical Character Recognition (OCR).

OCR is a quality-versus-speed trade-off. Multiple backends are available with different characteristics:

- **Tesseract** — local, CPU-only, fast, lower accuracy on complex layouts. Mature open-source OCR engine.
- **Ollama vision models** (DeepSeek-OCR, Qwen3-VL) — local, GPU-recommended, higher accuracy on complex layouts. Models hosted through Ollama.
- **OpenAI-compatible vision endpoints** (GPT-4o vision, LM Studio with vision models, vLLM with multimodal models) — highest accuracy, requires cloud or self-hosted endpoint, network latency.
- **Mock** — deterministic for testing.

The architecture documents establish that the system distinguishes canonical data (cannot be recreated) from derived data (regenerable, disposable). The system prompt template instructs the LLM to ground answers in the provided entity context. By analogy, the system must decide what part of an image-containing import is canonical.

Three patterns are possible:

1. **OCR text is canonical.** The extracted text is stored in the `Content` component. The image is not preserved.
2. **Image is canonical, OCR text is derived.** The image blob is stored (via `BinaryContent`). OCR text is generated on demand and can be regenerated. Re-running OCR with a different backend produces different text.
3. **Both image and OCR text are canonical.** Two components, both authoritative.

Pattern 1 loses the original image. Pattern 2 introduces derived data that may be discarded and regenerated. Pattern 3 creates two sources of truth that can drift.

The system already has a precedent for pattern 2 in the `BinaryContent` component (ADR-0011): binary data is referenced through a `BinaryContent` component, and text is extracted separately. PDFs are imported with both a `Content` component (extracted text) and a `BinaryContent` component (reference to the original file). The text extraction can be re-run with a better library in the future.

OCR extends this pattern: the image is the binary, the text is the extraction. Different OCR backends produce different extractions. The user may want to re-run OCR with a higher-quality backend (Tesseract → Ollama) when one becomes available locally.

The OCR backend must be pluggable for the same reason `ImportAdapter` is pluggable (ADR-0007): the system should not be coupled to a specific OCR engine. The user may prefer Tesseract for speed, Ollama for accuracy without network, or GPT-4o vision for highest accuracy. The choice is configuration, not code.

## Decision

OCR text is derived data. Image blobs are canonical (stored via `BinaryContent`). A new `OcrBackend` port trait defines the backend contract. The OCR pipeline is a derivation-layer (Layer 6) feature that produces `Content` components from `BinaryContent` references.

```rust
#[async_trait]
pub trait OcrBackend: Send + Sync {
    /// Recognize text from an image.
    async fn recognize(
        &self,
        image: &ImageInput,
    ) -> Result<OcrResult, OcrError>;

    /// The name of this backend (e.g., "tesseract", "ollama", "api", "mock")
    fn name(&self) -> &str;

    /// Whether this backend requires a network connection
    fn requires_network(&self) -> bool;
}

pub struct ImageInput {
    pub bytes: Vec<u8>,
    pub mime_type: String,
    pub width: u32,
    pub height: u32,
}

pub struct OcrResult {
    pub text: String,
    pub confidence: f64,         // 0.0-1.0
    pub blocks: Vec<TextBlock>,  // positional info for future highlighting
    pub model: String,           // e.g., "tesseract-5", "deepseek-ocr", "gpt-4o"
}

pub struct TextBlock {
    pub text: String,
    pub bbox: BoundingBox,       // x, y, width, height
    pub confidence: f64,
}
```

The initial backends are built-in (not plugin-routed):

- **TesseractBackend** — local, CPU-only. Uses `tesseract-rs` 0.3 with `build-tesseract` feature for self-contained compilation. Default backend.
- **OllamaBackend** — local, GPU-recommended. HTTP call to Ollama API. Configurable model (DeepSeek-OCR, Qwen3-VL).
- **ApiBackend** — cloud or self-hosted. HTTP call to OpenAI-compatible vision endpoint. Default `base_url` is `https://api.openai.com/v1`. Configurable to LM Studio, vLLM, etc.
- **MockBackend** — deterministic. Returns canned text for test images.

Backend selection is governed by an `OcrBackendFactory` similar to `create_chat_provider` (ADR-0023). Configuration is persisted through the application state.

### Image Canonical Storage

For standalone image imports (.png, .jpg, .gif, .bmp), the import creates an entity with:
- `BinaryContent` component — reference to the image file in object storage
- `Title` component — filename
- `Provenance` component — source path or URL

OCR runs asynchronously. When complete, the `Content` component is added with the extracted text. The `Content` component is derived — it can be regenerated by re-running OCR with a different backend.

For embedded images in office files (.docx, .pptx, .pdf), the import extracts the images, runs OCR on each, and merges the extracted text into the parent document's `Content` component. The images are referenced through `BinaryContent` on the parent entity. The OCR text becomes part of the document's `Content`, but the relationship to the source image is preserved in the `Provenance` component.

### Asynchronous Processing

OCR is slow (Tesseract: 100-500ms per image; Ollama: 1-5 seconds; API: 1-3 seconds). OCR runs asynchronously in a background task. The import operation returns immediately after the entity is created; OCR is queued and the `Content` component is updated when the task completes.

The entity's `Content` component is absent or partial until OCR completes. The frontend shows the import as "Processing image..." or "OCR pending" until the `Content` component is added. The pipeline emits an `OcrCompleted` event (derivation event) when OCR finishes, which triggers the embedding pipeline to generate embeddings for the new text.

### OCR Re-run

Because OCR text is derived, the user can re-run OCR with a different backend. The operation:
1. Loads the `BinaryContent` component from the entity.
2. Reads the image from object storage.
3. Calls the configured `OcrBackend`.
4. Replaces the `Content` component with the new extraction.

The previous `Content` is overwritten; the entity version increments. The audit trail records the OCR re-run as a `ComponentUpdated` event with `Provenance.ocr_backend` showing the new backend.

### OCR Pipeline Layer Ownership

| Sub-feature | Layer | Rationale |
|---|---|---|
| Image extraction from office files | 2 (Parsing) | Extracts binary blobs from structured containers |
| OCR backend call | 6 (Derivation) | Generates derived text from canonical image blobs |
| Content component update | 4 (Knowledge Model) | The derived text becomes a Content component on the entity |
| OCR completion event | 6 (Derivation event) | Signals derived data update |

OCR is a derivation activity. Image blobs flow up from Layer 2 (parsing extracts them from office files) and become canonical at Layer 4. OCR at Layer 6 produces derived text from the canonical image. The text becomes a `Content` component at Layer 4 — which is canonical for the entity but derived in the sense that it can be regenerated.

The distinction is: the *content* of the entity is canonical (it persists, is versioned, is queried). The *process* of generating the text from the image is derivation. A different OCR backend would produce different text — this is acceptable because the text is reproducible from the canonical image.

## Alternatives Considered

### Option 1: OCR text is canonical, image is not preserved

- Pros: Simpler storage. Only the text needs to be kept. The `Content` component is the authoritative representation of the document.
- Cons: Loses the original image. If OCR is wrong (misread a number, missed a chart label), the user cannot recover. A better OCR backend becomes available — the user cannot re-run OCR on the original. Images that are not text (photos, diagrams without text) are completely lost.
- Why not chosen: Violates the canonical/derived distinction. The image is the user's source data; OCR is a lossy interpretation. Losing the source to preserve the interpretation is a fundamental inversion of the canonical model.

### Option 2: Both image and OCR text are canonical

- Pros: The image is preserved. The OCR text is preserved. No derivation is needed — the text is stored once at import time.
- Cons: Two sources of truth that can drift. If the user re-runs OCR, the new text is a new canonical version, and the old text is archived. The drift is small (OCR is deterministic per backend) but it exists. The audit trail becomes complex — every OCR re-run is a canonical event.
- Why not chosen: Misclassifies derived data as canonical. The OCR text is a function of the image and the backend. Storing both creates a two-source-of-truth situation that the architecture explicitly avoids.

### Option 3: Image canonical, OCR text derived, no pluggable backend (single OCR library)

- Pros: Simpler implementation. One OCR library is integrated. No trait abstraction. Configuration is minimal.
- Cons: The OCR library is fixed at compile time. The user cannot switch to a better library without recompiling. The system is coupled to the OCR library's accuracy and licensing. Network-based OCR is not possible.
- Why not chosen: The use case demands backend choice. Office users with high-quality scanned documents benefit from Ollama or GPT-4o vision. CPU-only environments (CI, low-end laptops) require Tesseract. Mock backend is needed for testing.

### Option 4: Image canonical, OCR text derived, pluggable OcrBackend trait (chosen)

- Pros: Consistent with the `ImportAdapter` (ADR-0007), `ChatCompletion` (ADR-0023), and `VectorStore` (ADR-0017) adapter patterns. Backend selection is a configuration concern. The OCR text is regenerable, allowing future improvements in OCR quality. Mock backend enables testing.
- Cons: Adds a trait abstraction. The trait may need refinement as new backends expose new features. Backend-specific configuration (API keys, model names) is a separate concern that must be managed.
- Why chosen: Follows the established adapter pattern. The canonical/derived distinction is preserved. Backend choice is a user concern, not a code change. Future backends (cloud OCR services, new open-source models) are added as new implementations of the trait.

## Consequences

### Positive

- **OCR is regenerable.** When a better OCR backend becomes available, the user can re-run OCR on existing images. The previous text is overwritten; the canonical image is unchanged.
- **Backend choice is configuration.** The user selects Tesseract (CPU, local, fast), Ollama (GPU, local, higher accuracy), or API (cloud, highest accuracy) through application settings. The choice persists across restarts.
- **No data loss.** The image is the source. OCR is a lossy interpretation. The user can always inspect the original image even if OCR is wrong.
- **Testable pipeline.** The `MockBackend` enables deterministic tests. The OCR pipeline can be tested without a real Tesseract installation or network access.
- **Async processing.** OCR does not block the import. The user sees immediate feedback that the import is queued. The `Content` component appears when OCR completes.
- **Pluggable for new backends.** A new OCR service (Google Cloud Vision, Azure Cognitive Services) is added by implementing `OcrBackend`. No changes to the import pipeline or domain model.
- **Provider test endpoint.** The `set_provider` and `get_providers_status` operations from PRD-0007 verify OCR backend reachability and return latency. Misconfiguration is detected before first use.

### Negative

- **OCR adds latency to image imports.** Standalone image imports and office file imports with embedded images take longer because OCR runs in the background. The entity is available immediately, but `Content` is updated asynchronously.
- **OCR quality varies by backend.** Tesseract is less accurate on complex layouts. Ollama and GPT-4o vision are more accurate but slower. The user must understand the trade-off.
- **OCR failure handling.** If OCR fails (network error, unsupported image format, backend crash), the entity is created without a `Content` component. The user sees an error and can retry. The `Provenance` component records the OCR failure.
- **Backend-specific configuration.** API backends require an API key. Ollama backends require a model name. Tesseract is self-contained. The configuration UI must handle these differences.
- **Mock backend can mask real backend issues.** Tests that pass with mock may fail against Tesseract or Ollama. Integration tests must exercise real backends periodically.

### Risks

- **OCR quality on complex layouts:** Tesseract struggles with handwriting, rotated text, low-resolution scans. The user can switch to Ollama or API for higher accuracy, but the system cannot detect when Tesseract is failing silently (low confidence). Future enhancement: surface OCR confidence in the entity detail view.
- **Backend unavailability:** A network-based backend (Ollama, API) may be down. The `chat_test_provider`-equivalent operation (`set_provider` with `kind: "ocr"`) verifies reachability. A failed test displays clear setup instructions.
- **OCR cost:** API-based OCR (GPT-4o vision) costs per image. Large batch imports (e.g., a scanned book) may incur significant cost. The user must select the backend explicitly; the default is Tesseract (free, local).
- **Image storage growth:** The `BinaryContent` component preserves the original image. For a 1000-image import, the storage grows by the total image size. Existing storage capacity must accommodate this. Object storage with compression is recommended.
- **OCR GPU requirement:** Ollama vision models require GPU for acceptable speed. CPU inference is possible but very slow (10-30 seconds per image). The Ollama backend is documented as GPU-recommended with CPU fallback.
- **PII in images:** Office files may contain images with personal information (photos, ID documents). The `BinaryContent` preserves the image. The user is responsible for managing access. The `Permissions` component can be extended to restrict access to specific entities.
