# ADR-0027: Universal Import with Database Connectors and Column Mapping

**Status:** Proposed
**Date:** 2026-07-29
**Deciders:** Core maintainers

## Context

The initial import pipeline (ADR-0007) supports Markdown and PDF. The desktop app's import view imports only these two formats. Real office users work across an entire ecosystem of formats: Microsoft Office (Word, Excel, PowerPoint, Outlook), OpenDocument, Apple iWork, email exports, structured data, plain text, note-taking app exports, and databases.

PRD-0007 expands the import layer to cover this full ecosystem and adds three new import sources beyond local files: URLs, clipboard, and SQL databases. Each new source raises architectural questions that the initial ADR did not address:

- **Structured data formats (CSV, JSON, XML, YAML, database tables)** have user-defined columns. The same `Name` column might be the entity title, a tag, or the body. The importer cannot guess — the user must map columns to entity components. The mapping is per-import, not global.

- **Database connectors (SQLite, PostgreSQL, MySQL)** are not file imports. They are connections to live systems with credentials, schemas, and table selection. The import must support connection testing, table enumeration, and column mapping — all before any data is written.

- **URL import** fetches remote content. The content type is determined by HTTP headers, not file extension. The fetched content is then routed to the appropriate parser (HTML, PDF, image, text).

- **Clipboard import** accepts arbitrary text or HTML. The system detects format from content, not from file metadata.

- **Directory watching** triggers import when new files appear in a watched folder. This is a continuous import, not a one-shot operation.

- **Recursive directory import** is a UX concern: when a user selects a directory, do they want the top-level files or the full subtree? The answer is a toggle in the import view.

The existing `ImportAdapter` trait (ADR-0007) covers format-specific parsing but does not address column mapping, database connectivity, or URL/clipboard acquisition. These are pre-parsing concerns — they produce input that the existing adapters can consume. The new concerns can be modeled as pre-processing steps that feed the existing `ImportAdapter` pipeline.

The column mapping pattern applies uniformly to CSV, JSON, XML, YAML, and database tables. A single mapping UI is reused across all structured sources. The mapping is a per-import configuration: the user maps source columns to target components (Title, Tags, Content, Type). A "skip" option drops columns that are not relevant.

The universal import expansion also raises the question of how to handle the volume of new adapters. ADR-0016 (Plugin System Architecture) establishes that importers can be plugins. The initial universal import ships built-in adapters for the most common formats; less common formats (Notion JSON, specific email formats) are added incrementally. The plugin extension point remains open.

## Decision

The universal import layer extends ADR-0007's `ImportAdapter` trait. New adapters are added for the supported formats. Two new pre-processing abstractions are added for non-file sources: `RemoteSource` (URL fetch) and `DatabaseSource` (SQL connection). A new `ColumnMapping` type is added for structured data imports.

### Extended Format Coverage

The following adapters are added (all built-in, not plugin-routed at launch):

```text
Format Family        Adapters
─────────────────────────────────────────────────────────────────
Microsoft Office     DocxAdapter, DocAdapter, XlsxAdapter, XlsAdapter,
                     XlsmAdapter, PptxAdapter, PptAdapter, PpsAdapter,
                     MsgAdapter, PstAdapter, OstAdapter (metadata only)

OpenDocument         OdtAdapter, OttAdapter, OdsAdapter, OtsAdapter,
                     OdpAdapter, OtpAdapter, OdgAdapter

Apple iWork          PagesAdapter, NumbersAdapter, KeynoteAdapter

Email                EmlAdapter, MboxAdapter, IcsAdapter, VcfAdapter

Structured Data      CsvAdapter, JsonAdapter, XmlAdapter, YamlAdapter

Documents            RtfAdapter, TxtAdapter, HtmlAdapter, HtmAdapter,
                     MdAdapter (existing), PdfAdapter (existing)

Note-taking          EnexAdapter, OpmlAdapter, NotionJsonAdapter,
                     ObsidianVaultAdapter (directory of .md files)
```

Each adapter implements the existing `ImportAdapter` trait from ADR-0007. Adding a new format requires implementing the trait; no changes to the import pipeline or domain model.

### Database Source Abstraction

Database connectors are a new source type that produces a stream of structured rows for the column mapping step.

```rust
#[async_trait]
pub trait DatabaseSource: Send + Sync {
    /// Test the connection and return server metadata.
    async fn test_connection(&self) -> Result<ConnectionInfo, DatabaseError>;

    /// Enumerate tables (or equivalent: collections, sheets).
    async fn list_tables(&self) -> Result<Vec<TableInfo>, DatabaseError>;

    /// Preview rows from a table for the column mapping step.
    async fn preview_table(
        &self,
        table: &str,
        limit: usize,
    ) -> Result<TablePreview, DatabaseError>;

    /// Stream rows from a table for import.
    async fn stream_rows(
        &self,
        table: &str,
    ) -> Result<Box<dyn Stream<Item = Result<Vec<ColumnValue>, DatabaseError>> + Send + Unpin>, DatabaseError>;
}

pub struct ConnectionInfo {
    pub server_version: String,
    pub database_name: String,
    pub reachable: bool,
    pub latency_ms: u32,
}

pub struct TableInfo {
    pub name: String,
    pub row_count_estimate: u64,
    pub columns: Vec<ColumnInfo>,
}

pub struct ColumnInfo {
    pub name: String,
    pub data_type: String,
    pub nullable: bool,
}

pub struct TablePreview {
    pub columns: Vec<ColumnInfo>,
    pub sample_rows: Vec<Vec<ColumnValue>>,
}

pub enum ColumnValue {
    Text(String),
    Integer(i64),
    Float(f64),
    Boolean(bool),
    DateTime(DateTime<Utc>),
    Null,
}
```

The initial `DatabaseSource` implementations are built-in (not plugin-routed):

- **SqliteDatabaseSource** — accepts a file path. Uses `sqlx` with the `sqlite` feature.
- **PostgresDatabaseSource** — accepts a `postgresql://` connection string. Uses `sqlx` with the `postgres` feature.
- **MySqlDatabaseSource** — accepts a `mysql://` connection string. Uses `sqlx` with the `mysql` feature.

Connection strings are passed through unchanged to `sqlx::Any::connect`. Credentials are not logged. The connection is established, used for table listing and row streaming, then closed.

### Column Mapping

Structured data imports (CSV, JSON, XML, YAML, all databases) require the user to map source columns to entity components before import. The mapping is a per-import configuration.

```rust
pub struct ColumnMapping {
    /// Map a source column to a target component field.
    pub field_mappings: HashMap<String, FieldMapping>,

    /// Skip this column entirely (do not import).
    pub skip_columns: HashSet<String>,

    /// Override the entity type for all rows in this import.
    /// If None, the entity type is inferred or defaults to a generic "Record".
    pub entity_type_override: Option<String>,
}

pub enum FieldMapping {
    /// The column value becomes the entity Title.
    Title,
    /// The column value becomes part of the Description component.
    Description,
    /// The column value becomes the Content body (Markdown).
    Content,
    /// The column value is split on a delimiter and added to the Tags component.
    Tags { separator: String },
    /// The column value is stored in a custom component named by the user.
    CustomComponent { component_name: String },
    /// The column value becomes a Timeline event with the column as the date.
    TimelineDate,
}
```

The mapping UI shows the source columns on the left and the target field options on the right. The user drags or selects a target for each source column. A preview panel shows what the first entity will look like with the current mapping.

The mapping is stored as import metadata on each created entity's `Provenance` component. The mapping can be re-applied if the same source is imported again (e.g., a weekly CSV upload).

### URL Source

URL import fetches remote content, detects the content type from HTTP headers, and routes to the appropriate adapter.

```rust
pub struct UrlSource {
    pub url: String,
    pub method: HttpMethod,
    pub headers: HashMap<String, String>,
    pub timeout: Duration,
}

pub struct FetchedContent {
    pub bytes: Vec<u8>,
    pub mime_type: String,
    pub final_url: String,    // After redirects
}
```

The fetch step is a pre-processing concern, not a format concern. The fetched content is written to a temporary file with the inferred extension, then passed to the appropriate `ImportAdapter` based on the MIME type.

### Clipboard Source

Clipboard import accepts text or HTML content from the OS clipboard. The system detects format from content (presence of HTML tags indicates HTML).

```rust
pub enum ClipboardContent {
    Text(String),
    Html(String),
    Image(ClipboardImage),  // Future enhancement
}
```

HTML content is parsed by the existing `HtmlAdapter` (which extracts text, metadata, and links). Plain text is wrapped in a `Content` component. The clipboard content becomes a single entity (not a row-based import).

### Directory Watching

Directory watching is a continuous import that monitors a directory for new files.

```rust
pub struct WatchConfig {
    pub path: PathBuf,
    pub recursive: bool,
    pub file_patterns: Vec<String>,  // e.g., ["*.md", "*.pdf"]
    pub debounce: Duration,          // Wait this long after file changes before importing
}
```

The watch operation uses the OS file system events API (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows). When a new file is detected, the import pipeline is invoked with the file. The user is notified of each import. Failures are logged and shown in the import view.

### Recursive Directory Import

Directory imports (one-shot, not watched) have a recursive toggle:

```text
[ ] Include subdirectories (default: ON)

When ON: 42 files found (3 subdirectories)
When OFF: 12 files found (top-level only)
```

The toggle is shown in the import view when a directory is selected. The default is ON (most users expect recursive import). Single-file imports are unaffected.

### Conflict Detection

Re-importing a file that was previously imported produces a conflict. The system detects conflicts by:
- File path match (exact)
- Content hash match (for files moved or renamed)

When a conflict is detected, the user is shown options:
- **Skip** — do not import this file
- **Create new version** — import as a new entity version
- **Overwrite** — replace the existing entity's components

The decision is per-file; the user can mix choices across a batch.

### Undo Last Import

Every import operation records the entities it created. The undo operation archives all entities from the import in a single transaction.

```rust
pub struct ImportRecord {
    pub import_id: Uuid,
    pub started_at: DateTime<Utc>,
    pub completed_at: DateTime<Utc>,
    pub source: ImportSource,
    pub entity_ids: Vec<Uuid>,
    pub relationship_ids: Vec<Uuid>,
    pub component_ids: Vec<Uuid>,
}
```

The `undo_import` IPC command loads the import record, archives all referenced entities, and removes the record. A confirmation dialog is shown (F6.5 forgiveness principle).

## Alternatives Considered

### Option 1: Single monolithic universal importer

- Pros: All format logic in one crate. One team owns the import pipeline end-to-end.
- Cons: The codebase becomes unmaintainable as formats are added. A bug in one format affects all others. Testing requires exercising all formats. New contributors cannot add formats without understanding the entire pipeline.
- Why not chosen: Violates the adapter pattern. Creates a fragile, untestable monolith.

### Option 2: Plugin-only model — no built-in adapters

- Pros: Core is minimal. All formats are plugins. Consistent with ADR-0016.
- Cons: The user must install plugins for every format they use, even common ones (Markdown, PDF, CSV). The "import any document" experience requires a plugin marketplace that does not exist. The launch experience is broken — the user cannot import anything out of the box.
- Why not chosen: The launch experience requires built-in support for common formats. Plugin extensibility is preserved for less common formats.

### Option 3: Format-specific CLIs (separate `kos-import-csv`, `kos-import-db`, ...)

- Pros: Each format has its own CLI tool. Independent versioning. Clear separation.
- Cons: The user must know which CLI to use for each format. The desktop app must orchestrate many CLIs. Configuration is scattered. The architecture loses the unified import pipeline.
- Why not chosen: The desktop app and CLI both need a unified import entry point. Format-specific CLIs fragment the user experience and the codebase.

### Option 4: Built-in ImportAdapter extensions plus DatabaseSource and ColumnMapping abstractions (chosen)

- Pros: Extends the proven `ImportAdapter` pattern (ADR-0007) to new formats. Database and column mapping concerns are isolated as pre-processing steps. The column mapping UI is reused across CSV, JSON, XML, YAML, and databases. The plugin extension point remains open for community formats.
- Cons: The import layer grows. The crate (`knowledge-import`) must maintain many adapters. The `DatabaseSource` trait adds a new abstraction that may evolve as database features are added.
- Why chosen: Consistent with the established adapter pattern. Common formats are built-in. Less common formats can be added as plugins without core changes. The user experience is unified — one import entry point for all formats.

## Consequences

### Positive

- **Office users can import their actual documents.** The "try at home, bring to work" value proposition is realized. Microsoft Office, OpenDocument, and Apple iWork formats are supported. The user does not need to convert files before import.
- **Database import enables business workflows.** Connecting to a SQLite, PostgreSQL, or MySQL database and importing tables as entities is a common business use case. The column mapping UI makes the workflow accessible to non-technical users.
- **URL and clipboard import reduce friction.** Pasting a URL or clipboard content is faster than downloading and importing. The format auto-detection handles the routing.
- **Column mapping is reusable.** The same mapping UI works for CSV, JSON, XML, YAML, and databases. Users learn one UI for all structured imports.
- **Conflict detection prevents accidental duplicates.** Re-importing the same file is a common operation. The conflict options (skip, new version, overwrite) give the user control.
- **Undo import is reversible.** The user can experiment with imports without fear of permanent damage. The `ImportRecord` stores the entities for undo.
- **Directory watching enables continuous import.** New files in a watched folder are automatically imported. Useful for sync folders, download directories, and team collaboration.
- **Format auto-detection by magic bytes.** Files without recognized extensions are inspected by magic bytes. The system warns on unknown formats rather than failing silently.
- **Recursive toggle respects user intent.** The user can choose top-level only or full subtree. The default (ON) matches the most common expectation.

### Negative

- **Many adapters to maintain.** The `knowledge-import` crate grows to ~30 adapters. Each adapter is independently testable but requires maintenance for upstream format changes (e.g., Office Open XML schema updates).
- **Office format parsing quality varies.** `.docx` extraction is well-supported by `docx-rs`. `.xlsx` is well-supported by `calamine`. `.pptx` is less mature. Apple iWork formats require bundle parsing (zip of XML). Some formats (`.numbers`, `.key`) are reverse-engineered and may break with new iWork versions.
- **Database credentials are handled by the import process.** The connection string contains the password. The import pipeline must not log the password. The desktop app stores the connection string securely (OS keychain) for repeated imports.
- **Network imports (URL) introduce network failures.** The fetch step can fail with timeouts, DNS errors, or HTTP errors. The error message must be clear about which step failed.
- **Directory watching requires OS file system events.** Each OS has a different API. The watch implementation must be cross-platform. The `notify` crate (or equivalent) abstracts the platform differences.
- **Column mapping is per-import.** The mapping is not persistent across imports of the same source. The user re-maps each time. A future enhancement could save mappings by source fingerprint (e.g., CSV file hash) for auto-apply.
- **Undo import only affects the most recent import.** The undo operation does not support undoing multiple imports. A future enhancement could extend the import history.
- **OCR is not part of this ADR.** OCR for images within office files is covered by ADR-0026. This ADR focuses on format coverage and structured data sources.

### Risks

- **Format-specific parsing bugs:** A `.docx` file with complex formatting may not import correctly. The fallback is to extract the text only. The `BinaryContent` preserves the original file so the user can inspect it.
- **Database schema changes:** If the source database schema changes between imports, the column mapping may become invalid. The mapping UI shows a warning if a previously mapped column is missing. The user can re-map or skip.
- **URL import of large files:** A URL pointing to a large file (e.g., 1GB PDF) may exhaust memory or time. The fetch step has a size limit and a timeout. Large files are not imported via URL — the user must download first.
- **Directory watching flood:** A directory with many new files may overwhelm the import queue. The watch implementation debounces file events and processes them sequentially.
- **PST/OST metadata-only:** The PRD specifies that PST and OST files import metadata only (folder structure, sender, subject, date) but not full email body. This is a known limitation of the initial release. Full PST parsing is a future enhancement.
- **Notion JSON format changes:** Notion's export format is not formally documented. The parser is reverse-engineered and may break with Notion updates. The error handling surfaces a clear "unsupported Notion format" message.
- **iWork format reverse engineering:** Apple iWork formats (`.pages`, `.numbers`, `.key`) are not open standards. The parser handles common structures but may miss edge cases. New iWork versions may break parsing.

## Related Decisions

- **ADR-0002:** Storage Independence via Adapter Pattern — all import adapters are accessed through the `ImportAdapter` trait.
- **ADR-0005:** Compiler-Inspired Architecture — the import layer is Layer 1 of the seven-layer pipeline. Database connectors and URL fetch are pre-processing steps that produce input for the existing adapters.
- **ADR-0007:** Multi-Format Import via ImportAdapter Trait — the new adapters extend the existing trait. The `ImportAdapter` interface is unchanged.
- **ADR-0008:** Fuzzy Entity Resolution with Confidence Scoring — newly imported entities are matched against existing entities through the same resolution pipeline.
- **ADR-0011:** BinaryContent Component — the original file (office document, email, database export) is preserved through the `BinaryContent` component. The extracted text is the `Content` component.
