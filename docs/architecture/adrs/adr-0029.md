# ADR-0029: Centralized Entity Type Color Mapping via CSS Custom Properties

**Status:** Proposed
**Date:** 2026-07-30
**Deciders:** Core maintainers
**Related PRD:** PRD-0008

## Context

The desktop application renders entity type badges, graph node colors, timeline dots, and search result indicators across 7 of 13 views. Each view currently defines its own color mapping independently:

- Dashboard: hardcoded `typeColors = ["#3b82f6", "#10b981", ...]` array indexed by position
- Graph: hardcoded `colorMap: Record<string, string>` with per-type hex values
- Timeline: hardcoded `typeColors` array assigned dynamically by first-seen order
- Browser, Detail, Tree, Table, Search: all use `var(--accent)` for every type

The design system (`docs/engineering/ui-design-system.md`) defines per-entity-type color tokens (`--color-entity-concept: #8B5CF6`, `--color-entity-person: #EC4899`, etc.). These tokens are not used by any view. The result is visual inconsistency: the same entity type appears in different colors across different views.

## Decision

Centralize entity type color mapping in `desktop/src/lib/theme.svelte.ts` as a single function `getEntityTypeColor(type: string): string` that maps entity types to CSS custom property references. All views call this function instead of maintaining their own color arrays or maps.

The mapping uses CSS custom property references (`var(--color-entity-concept, #8B5CF6)`) with fallback values, ensuring that:

1. Colors are defined once in the design system CSS
2. Dark mode and theme changes propagate automatically
3. Unknown entity types fall back to `--color-entity-default`
4. No view hardcodes hex values for entity types

```typescript
const entityTypeColorTokens: Record<string, string> = {
  Concept:      "var(--color-entity-concept, #8B5CF6)",
  Person:       "var(--color-entity-person, #EC4899)",
  Organization: "var(--color-entity-organization, #F59E0B)",
  Project:      "var(--color-entity-project, #6366F1)",
  Paper:        "var(--color-entity-paper, #3B82F6)",
  Book:         "var(--color-entity-book, #06B6D4)",
  Tool:         "var(--color-entity-tool, #10B981)",
  Technology:   "var(--color-entity-technology, #6366F1)",
  Decision:     "var(--color-entity-decision, #EF4444)",
  Event:        "var(--color-entity-event, #F97316)",
  Collection:   "var(--color-entity-collection, #14B8A6)",
};

export function getEntityTypeColor(type: string): string {
  return entityTypeColorTokens[type] ?? "var(--color-entity-default, #64748B)";
}
```

## Alternatives Considered

### Option 1: Per-view color arrays (current approach)
- Pros: No shared dependency; each view is self-contained
- Cons: Colors are inconsistent across views; design system tokens are ignored; dark mode requires updating every view independently
- Why not chosen: Produces visual inconsistency; violates the design system; 7 views must be updated independently when a color changes

### Option 2: Tailwind-style utility classes for entity colors
- Pros: Declarative; no JavaScript needed; CSS-only
- Cons: Requires Tailwind or equivalent utility framework; adds build complexity; not currently part of the stack
- Why not chosen: The project uses Svelte scoped styles and CSS custom properties, not a utility framework. Adding Tailwind would be a larger architectural change.

### Option 3: Runtime theme object with hex values
- Pros: Centralized; works in JavaScript context (e.g., SVG fill)
- Cons: Does not respond to CSS media queries or theme changes automatically; requires JS re-render on theme change
- Why not chosen: CSS custom properties (`var()`) respond to theme changes automatically without JS re-render. Using `var()` references in the mapping preserves reactivity.

## Consequences

### Positive
- Single source of truth for entity type colors
- Design system tokens are respected across all views
- Dark mode and theme changes propagate automatically
- Adding a new entity type requires one change (the mapping function)
- Reduces code duplication across 7+ views

### Negative
- All views depend on `theme.svelte.ts` for color resolution
- CSS custom properties must be defined in `app.css` for all entity types
- SVG contexts (graph nodes) require `style` attributes with `var()` rather than inline hex values

### Risks
- If CSS custom properties are not defined, fallback hex values are used — this is acceptable but may produce inconsistent colors across themes
- Graph view SVG rendering with `var()` in `fill` attributes requires testing in all browsers
