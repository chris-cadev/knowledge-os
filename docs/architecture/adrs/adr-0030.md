# ADR-0030: Shared Frontend Component Library for View Consistency

**Status:** Proposed
**Date:** 2026-07-30
**Deciders:** Core maintainers
**Related PRD:** PRD-0008

## Context

The desktop application has 13 views. UX audits (`docs/engineering/ux-audits/`) found that common UI patterns are re-implemented independently in each view with inconsistencies:

- **Type badges** are rendered in 10 views, each with different styling and colors
- **Type filters** are implemented in 5 views — 4 use free-text `<input>`, 1 uses `<select>` (correctly), and 1 has an empty `<select>` (broken)
- **Entity selection** is needed in Graph view (currently a UUID text input) and should be reusable
- **Skeleton loaders** are needed in 4 views — Timeline has an excellent implementation, but others use plain text "Loading..."

Without shared components, each view must be updated independently when a pattern changes. The audits identified 31 major (P1) issues that are largely duplicates of the same pattern violation across different views.

## Decision

Create four shared Svelte components in `desktop/src/components/` that encapsulate the common patterns. All views use these components instead of implementing patterns independently.

### Components

**`TypeBadge.svelte`** — Entity type badge with design system color.

```svelte
<script lang="ts">
  import { getEntityTypeColor } from "../lib/theme.svelte.js";
  let { type }: { type: string } = $props();
</script>
<span class="type-badge" style="background: {getEntityTypeColor(type)}">{type}</span>
```

**`TypeFilterDropdown.svelte`** — Dropdown filter populated from available entity types.

```svelte
<script lang="ts">
  let { value, options, onchange }: {
    value: string;
    options: string[];
    onchange: (value: string) => void;
  } = $props();
</script>
<select bind:value onchange={() => onchange(value)}>
  <option value="">All types</option>
  {#each options as opt}<option value={opt}>{opt}</option>{/each}
</select>
```

**`EntityPicker.svelte`** — Autocomplete entity search with keyboard navigation.

```svelte
<script lang="ts">
  import { searchEntities } from "../lib/api.js";
  import type { EntitySummary } from "../lib/types.js";
  let { onSelect, placeholder }: {
    onSelect: (entity: EntitySummary) => void;
    placeholder?: string;
  } = $props();
  // ... search, debounce, keyboard nav, dropdown rendering
</script>
```

**`SkeletonLoader.svelte`** — Configurable skeleton with layout variants.

```svelte
<script lang="ts">
  let { variant, count = 3 }: {
    variant: "grid" | "table" | "list" | "card";
    count?: number;
  } = $props();
</script>
```

### Integration

Each view imports the relevant shared components. The view provides data (entity types, options, search results) and the component handles rendering and interaction.

### Location

Components live in `desktop/src/components/` — a new directory alongside `desktop/src/views/` and `desktop/src/lib/`.

## Alternatives Considered

### Option 1: Continue per-view implementations
- Pros: No shared dependency; each view can evolve independently
- Cons: 31+ P1 issues repeat across views; fixing a pattern requires editing 5-10 files; visual inconsistency persists
- Why not chosen: The audits show this approach produces inconsistency. Fixing the same issue in 5 views independently is wasteful and error-prone.

### Option 2: Headless UI library (e.g., Headless UI, Radix)
- Pros: Battle-tested accessibility; keyboard navigation built-in; consistent behavior
- Cons: Adds external dependency; may not match the project's design tokens without extensive customization; React/Vue-oriented libraries don't work with Svelte 5
- Why not chosen: The Svelte ecosystem has fewer headless UI options. Building four focused components is simpler than integrating a library and customizing it.

### Option 3: Svelte component library package (separate npm package)
- Pros: Reusable across projects; versioned independently; clean separation
- Cons: Premature for a single-project component set; adds build and publish overhead; no second consumer exists
- Why not chosen: There is only one consumer (the desktop app). A separate package adds complexity without benefit. If a second consumer emerges, the components can be extracted later.

## Consequences

### Positive
- Four components replace ~500 lines of duplicated code across views
- Fixing a pattern (e.g., type badge color) requires one change
- New views can reuse components for consistent UX
- Accessibility improvements (keyboard nav, ARIA) are centralized
- Audits can verify compliance by checking component usage

### Negative
- Views depend on shared components — a breaking change to a component affects all consumers
- Component API must be designed carefully to accommodate all view requirements
- New contributors must learn the component library

### Risks
- Component API may need revision as views are integrated — mitigate by building components first, then integrating one view at a time
- Entity picker performance with 100K entities — mitigate with debounced server-side search (300ms)
- Skeleton variant may not match every view's layout — mitigate with configurable `variant` prop and custom slot content
